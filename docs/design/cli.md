# uptime-kuma-cli design

## Goal

- Operate an Uptime Kuma 1.23 or 2.x instance from the shell and from agents without writing ad hoc `uptime-kuma-api` scripts; version-specific behaviour is qualified inline where the two differ
- Cover what existing CLIs lack: proxies, notification tests, and status changes (important heartbeats)

## Why not an existing CLI

- BigBoot/AutoKuma `kuma` (Rust): monitors and notifications via JSON files; no beats, no status changes, no proxies, no notification test; targets Kuma v2 by default since 2.0.0
- pablofmorales/kuma-cli (TypeScript): monitors and beats, but no proxies, no notification edit/test, no keyword / json-query fields, and it stores the login token in its config file

## Transport

- Socket.IO v4 client (`socket.io-client`) against the Kuma base URL, `transports: ["websocket"]`
- Kuma 1.23 has no OpenAPI / REST API for management (only badge, push, status page and metrics are REST), so the CLI talks Socket.IO
- Log in with `login` `{ username, password, token: "" }`; the callback returns `{ ok, msg }`. On 2.x a failed login's `msg` is an i18n key (`authIncorrectCreds` or `authInvalidToken`, sent with `msgi18n: true`) where 1.x sent English; the CLI maps the two known keys back to the 1.x texts, so a bad login reads the same on both versions. With 2FA enabled Kuma answers `{ tokenRequired: true }` instead of `ok`; the CLI then resolves a TOTP (Configuration below) and re-sends `login` with `token` set. The tokenless first attempt is required: `tokenRequired` is the only signal that a token is needed, and a token sent up front would run Kuma's token-verify branch even for `twofa_status === 0` accounts — a second `afterLogin` when the stored secret still verifies — as well as `totp_*` commands for accounts that do not need them
- After login the server pushes `monitorList` (object keyed by id), `maintenanceList` (object keyed by id), `notificationList` (array), `proxyList` (array), `dockerHostList` (array), `apiKeyList` (array of `APIKey.toPublicJSON` rows — `active` is the BOOLEAN column's 0/1, `status` is the computed `active` / `inactive` / `expired`, the stored secret `key` is never sent), then `statusPageList` (object keyed by id) about 500ms later — on 1.x; on 2.x every list is pushed before the login ack instead — then one `heartbeatList (monitorID, beats)` per monitor plus one `importantHeartbeatList (monitorID, beats)` on 1.x only. Then `Monitor.sendStats` emits per monitor in monitorList order `avgPing (monitorID, ms)`, `uptime (monitorID, 24, ratio)` and `uptime (monitorID, 720, ratio)` — 2.x adds `uptime (monitorID, "1y", ratio)` since 2.0.0 and `domainInfo (monitorID, daysRemaining, expiryDate)` since 2.1.0 for a monitor whose domain has an RDAP expiry — plus `certInfo (monitorID, info_json)` only when a `monitor_tls_info` row exists; the sends are awaited one monitor at a time on 1.x (2.x computes them in memory concurrently and they all land before the login ack), `sendStats` also runs on every heartbeat so the pushes repeat, and `afterLogin`'s `for...in` sends the id as a string (the heartbeat path sends a number — the CLI accepts both). There is no pushed tag list: each monitor's `tags` is the `monitor_tag`⋈`tag` join (`{ id, monitor_id, tag_id, value, name, color }`, ordered by tag name — the server's ORDER BY on 1.x; the join has none on 2.x, where the CLI sorts them itself) and the tag table itself is only readable through `getTags`
- The CLI waits after login only for the lists the command reads: `monitorList`, `notificationList`, `proxyList` and `dockerHostList` for every command, `maintenanceList` for the maintenance commands, `apiKeyList` for the api-keys commands that check or print it, `statusPageList` for `maintenance status-pages`, every `status-pages` command and `settings set` when its `entryPage` override names a status page — waiting for `statusPageList` unconditionally would add its ~500ms delay (1.x only) to every command
- Request events used, all with a trailing callback returning `{ ok, msg, ... }`:
    - `add (monitor)` → `monitorID`
    - `editMonitor (monitor)` → `monitorID`
    - `getMonitor (id)` → `monitor`
    - `pauseMonitor (id)` / `resumeMonitor (id)`
    - `getMonitorBeats (id, hours)` → `data` (oldest first, raw heartbeat rows with `important`)
    - `addNotification (notification, idOrNull)` → `id`; the server stores the whole object as the `config` JSON string
    - `testNotification (notification)` → `msg`
    - `addProxy (proxy, idOrNull)` → `id`
    - `deleteMonitor (id)` / `deleteNotification (id)` / `deleteProxy (id)`
    - `clearHeartbeats (id)` → `{ ok }` — DELETEs the monitor's heartbeat rows, then re-pushes `heartbeatList` (newest 100, overwrite); `clearEvents (id)` → `{ ok }` — resets `msg` / `important` on them (the rows stay for uptime), then re-pushes `importantHeartbeatList` (overwrite) on 1.x only; both answer ok even for an unknown monitor id. `clearStatistics ()` → `{ ok }` — DELETEs the whole heartbeat table, no re-push. On 2.x clearHeartbeats and clearStatistics also clear the stat tables and restart active monitors, while clearEvents only resets msg and important
    - `getDatabaseSize ()` → `{ ok, size }` — the sqlite file's size in bytes (0 on a 2.x non-sqlite backend, which the CLI refuses); `shrinkDatabase ()` → `{ ok }` — SQLite `VACUUM`; on 1.23.17 the ack precedes VACUUM completion (the handler is not awaited, so a failed VACUUM surfaces only as a Kuma-side unhandled rejection), on 2.x it follows it
    - `addDockerHost (dockerHost, dockerHostID)` → `{ ok, msg, id }` — `dockerHostID` null adds a host, an existing id overwrites it (`DockerHost.save` reads `name` / `dockerType` / `dockerDaemon`); a successful save re-pushes `dockerHostList`. `testDockerHost (dockerHost)` → `{ ok, msg }` without re-pushing. `deleteDockerHost (id)` → `{ ok, msg }`, re-pushes `dockerHostList` and sets `docker_host` null on the monitors that used the host; an unknown or foreign id answers `ok:false "docker host not found"`
    - `addAPIKey ({ name, expires, active })` → `{ ok, msg, key, keyID }` — `key` is the one-time clear key `uk<id>_<nanoid(40)>`, the server stores only its hash and enables `apiKeysEnabled` itself; `enableAPIKey (id)` / `disableAPIKey (id)` / `deleteAPIKey (id)` → `{ ok, msg }`, each re-pushing `apiKeyList`. All three answer ok even when the id matches nothing (the UPDATE/DELETE affects 0 rows), and enable/disable do not even scope by user — the pushed list is the only guard. `getAPIKeyList` exists but only re-pushes the list `afterLogin` already sent, so the CLI reads the push like the other lists
    - `getTags ()` → `tags` (`{ id, name, color }` rows)
    - `addTag ({ name, color })` → `tag`; `editTag ({ id, name, color })` → `tag` (overwrites both fields, `ok:false "Tag not found"` for an unknown id on 1.x — the 2.x msg is the i18n key `tagNotFound`, printed as-is); `deleteTag (id)` answers ok even for an unknown id
    - `addMonitorTag (tagID, monitorID, value)` / `editMonitorTag (tagID, monitorID, value)` / `deleteMonitorTag (tagID, monitorID, value)`; none of them pushes `monitorList` again, so the CLI's pushed copy goes stale within a run (each command logs in once, so the next run sees the new state)
    - `addMaintenance (maintenance)` → `maintenanceID`; `editMaintenance (maintenance)` runs `jsonToBean`, which overwrites every field it reads, so an edit sends the whole fetched object; `getMaintenance (id)` → `maintenance`; `deleteMaintenance (id)` / `pauseMaintenance (id)` / `resumeMaintenance (id)` answer `{ ok, msg }`
    - `getMonitorMaintenance (id)` → `monitors` (`{ id }` rows); `addMonitorMaintenance (id, [{ id }])` DELETEs the maintenance's `monitor_maintenance` rows and INSERTs the sent ids — it replaces the whole set, it does not add
    - `getMaintenanceStatusPage (id)` → `statusPages` (`{ id, title }` rows); `addMaintenanceStatusPage (id, [{ id }])` replaces the `maintenance_status_page` set the same way
    - `getStatusPage (slug)` → `config` (`StatusPage.toJSON`); `addStatusPage (title, slug)` → `{ ok, msg }` only; `saveStatusPage (slug, config, imgDataUrl, publicGroupList)` → `{ ok, publicGroupList }` (the sent groups mutated with their ids); `deleteStatusPage (slug)` → `{ ok }`; `postIncident (slug, { title, content, style })` → `incident` (`Incident.toPublicJSON`); `unpinIncident (slug)` → `{ ok }`. 2.1.0 adds `getIncidentHistory (slug, cursor)` → `{ incidents, total, nextCursor, hasMore }` (pages of `INCIDENT_PAGE_SIZE` = 10, `created_date` DESC, the cursor being the page's last `created_date`), `editIncident (slug, incidentID, incident)` → `incident`, `resolveIncident (slug, incidentID)` → `incident`, and `deleteIncident` (not used by the CLI). None of them re-pushes `statusPageList` — `sendStatusPageList` only runs in `afterLogin`
    - `getSettings ()` → `data` (the general settings object, `serverTimezone` filled from the server when unset); `setSettings (data, currentPassword)` → `{ ok, msg }` — `Settings.setSettings` upserts only the keys present in `data`, but the handler also reads `disableAuth`, `entryPage`, `chromeExecutable`, `nscd` and `serverTimezone` unconditionally, so a partial object would reset `entryPage`, restart Chrome, toggle nscd and could disconnect every other client
- A request whose callback has `ok: false` exits 1 with `msg` on stderr

## Configuration

- `$XDG_CONFIG_HOME/uptime-kuma-cli/config.toml` (or `~/.config/uptime-kuma-cli/config.toml`)
    - `url`, `username_command`, `password_command`, `totp_command`, `totp_secret_command`
- `*_command` runs with `sh -c`; the first stdout line, minus a trailing `\r`, is the value (spaces are kept). An env value takes precedence and the command does not run
- 2FA login (TOTP): only after the tokenless `login` answers `tokenRequired` does the CLI resolve a token and retry `login`. The first configured source wins: `UPTIME_KUMA_TOTP`, then `totp_command`, then `totp_secret_command`; none configured exits 2 naming all three
    - `totp_command` prints a ready one-time token; `totp_secret_command` prints the base32 secret — or a whole `otpauth://` URI — and the CLI derives the token itself: HMAC-SHA1 over the 30-second counter, 6 digits, the same shape `notp.totp.verify` checks with `{ window: 1, time: 30 }`, so ±1 period of clock skew is tolerated. A URI is used only when it asks for exactly this shape (TOTP, SHA-1, 6 digits, 30 s period, option names spelled lowercase and not repeated) — anything else exits 2 — and ready tokens from `UPTIME_KUMA_TOTP` / `totp_command` are trimmed; a blank `UPTIME_KUMA_TOTP` counts as unset, like the other env credentials
    - Kuma rejects a token equal to the last accepted one (`twofa_last_token`) and a TOTP repeats every 30 s, so two logins inside one window collide; on an invalid-token answer — `Invalid Token!` on 1.x, the i18n key `authInvalidToken` on 2.x — a secret-minted token is retried with the adjacent counters' values — previous window first, then next, so a client clock ahead of the server still has a retry inside the server's ±1 window; the previous code — usually already off the user's screen — is spent before the next one, each differing and verifying while the skew stays inside that window. `UPTIME_KUMA_TOTP` / `totp_command` tokens cannot be re-minted, so pace those past the window like the login rate limit already requires
    - a wrong token is an ordinary login failure: Kuma answers `{ ok: false, msg: "Invalid Token!" }` on 1.x or `{ ok: false, msg: "authInvalidToken", msgi18n: true }` on 2.x, and the CLI exits 2
    - the CLI keeps the TOTP secret out of its own argv, stdout, stderr and socket calls — the secret does pass through `totp_secret_command`'s stdout by design, so the command string itself should read it from a file or keychain rather than embed it (an embedded secret sits in config.toml and the child's argv); command output is handled like the other `*_command` secrets (failure reports only that the command failed, timed out or printed nothing), and `UPTIME_KUMA_TOTP` is stripped from `*_command` children like the login secrets
    - TOTP sources run only after `tokenRequired`, so accounts without 2FA never execute a `totp_*` command even when one is configured
- Each command logs in once — for a 2FA account that is up to four `login` events (tokenless, token, two adjacent-window retries). Kuma limits logins to 20 per minute for the whole instance, so a loop of many commands can lock out the UI login for a while
- With an `http://` URL the login travels in clear text — credentials and, on a 2FA account, the TOTP token (and its adjacent-window retries) included; use `https://` when the path leaves a trusted network, and treat it as required for a remote host with 2FA
- Env: `UPTIME_KUMA_URL`, `UPTIME_KUMA_USERNAME`, `UPTIME_KUMA_PASSWORD`, `UPTIME_KUMA_TOTP` (a ready one-time token for accounts with 2FA), `UPTIME_KUMA_TIMEOUT` (seconds, default 30, for connect + login + each request), `UPTIME_KUMA_COMMAND_TIMEOUT` (seconds, default 60), `UPTIME_KUMA_SHRINK_TIMEOUT` (seconds, default 600 — only `database shrink`'s ack wait; on 2.x VACUUM is not bounded by Kuma's own timeouts)
- The username command does not see the password and vice versa

## Output

- stdout is JSON (pretty, 2-space indent), stderr is for messages
- `notificationIDList` is always printed as a sorted array of numbers, whether Kuma sent `{ "3": true }` or `[3]`
- Monitor `tags` print as `[{ tagId, name, value }]`, normalized from the `monitor_tag`⋈`tag` join rows Kuma sends
- Notification configs and proxy passwords are never printed
- Monitor fields that hold secrets (`basic_auth_pass`, `oauth_client_secret`, `tlsKey`, `headers`, `body`, `grpcBody`, `grpcMetadata`, `mqttPassword`, `radiusPassword`, `radiusSecret`, `databaseConnectionString`, the Kuma 2.x fields `bearer_token`, `gamedigToken`, `rabbitmqPassword`, `sshPassword`, `sshPrivateKey` and `sshPassphrase`, and every `kafkaProducerSaslOptions` value other than `mechanism` / `username` / `awsRegion` / `accessKeyId`) print as `"***"` when non-empty; `pushToken` stays visible because pushers need it
- A password inside a monitor `url` (`https://user:pass@host/` or a lone `https://token@host/` → `https://***@host/` — either userinfo slot can hold a token, so both are hidden) prints as `***` in `monitors list` / `get` / `edit` and in the `publicGroupList` monitors of `status-pages get` / `save` (Kuma adds the url there when `sendUrl` is on)
- `steamAPIKey` and `globalpingApiToken` in `settings get` / `settings set` output print as `"***"` when non-empty, and userinfo inside `primaryBaseURL` prints as `***` like a monitor url; these are the secrets among the general settings
- The same redaction applies to a userinfo secret inside a docker host's `dockerDaemon` (`https://u:p@host:2376`) in every `docker-hosts` output, and to the daemon value Kuma's `testDockerHost` error `msg` can echo — a socket connect error carries `socketPath` verbatim and an axios error can carry the `tcp://`→`http://` patched baseURL, so both forms are masked in the exit-1 message
- An API key's clear value prints only in the `api-keys add` result — the server stores just the hash, so no list or later command can show it; `add` also warns on stderr that it cannot be read again

## Exit codes

| code | meaning |
|---|---|
| 0 | done |
| 1 | Kuma answered no (`ok: false`, unknown id) |
| 2 | configuration, usage (including a missing subcommand), connection, login, disconnect, or timeout failure |
| 3 | a create or attach was skipped because it already exists (`monitors add` / `tags add` / `maintenance add` same name or title, `status-pages add` same slug, `status-pages save` slug rename onto another page, `monitors tag` same tag+value) |
| 70 | unexpected error |

## Commands

- Where a command takes a monitor id or a notification id — a `<id>` argument, `--parent`, `--notifications-from`, `--notification-id`, or the monitor targets of `maintenance monitors` (`--add` / `--remove` / `--set-ids`; `--set-ids` splits its value on commas before resolving, so a name containing a comma is unreachable there) — the value may be the positive integer id or the resource's exact name from the pushed `monitorList` / `notificationList`. A positive integer always stays an id, so a resource literally named `"123"` cannot be picked by name (other numeric-looking strings like `"0"` or `"007"` are name candidates). A name matching no row exits 2 (`no monitor named "<name>"` — exact match means a missing name has no candidates to list), and a name matching more than one exits 2 listing the candidate ids (`monitor name "<name>" is ambiguous: ids 1, 2`) — the pushed lists are the only source, no search event is sent, and matching is exact (a substring does not match). `--set` / `--config-file` fields keep the wire format, so a `parent` key or a `notificationIDList` entry there stays numeric — names are not resolved in hatch fields. `--parent` reserves `none` (it clears the parent), so a group literally named `none` cannot be picked by name. Proxies have no name field in Kuma 1.23.17 — `proxyList` rows carry host / port / credentials only — so proxy ids stay numeric everywhere, as do the ids of every other resource (maintenance windows, tags, docker hosts, api keys, status pages; status pages are addressed by slug in their own commands)

- Every numeric flag value, in every command, is a decimal literal only — `0x10`, `1e2`, signs and surrounding whitespace exit 2 before connecting (`Number()` would take them). In `monitors add` / `edit` the same parsers back the hatch values of keys that have a typed flag: a quoted string there is held to the same rule, while a JSON number (`{"interval": 1e2}`) is accepted by value — it is written out in plain decimal before the check, and one with more than 100 decimal places (`1e-101`) exits 2 rather than being rounded

### monitors

- `monitors list [--name <substring>] [--tag <name>]`
    - array sorted by id of `{ id, name, type, active, url, hostname, port, interval, parent, notificationIDList, tags }`; `tags` is `[{ tagId, name, value }]` from the monitor's `monitor_tag`⋈`tag` join
    - `--name` filters case-insensitively; `--tag` keeps monitors that have a tag whose name equals the argument exactly (case-sensitive); the two combine
- `monitors get <id|name>`: the monitor object from `monitorList` with `notificationIDList` as an array and `tags` as `[{ tagId, name, value }]`; unknown id exits 1
- `monitors stats [id|name]`: uptime, ping and certificate stats from the pushed `avgPing` / `uptime` / `certInfo` events; no id prints an array of every monitor in monitorList order, an id prints one object, unknown id exits 1
    - waits for `avgPing`, `uptime` 24 and `uptime` 720 of every requested monitor until the timeout like `beats latest` — missing ones exit 2 naming them; only this command waits for the stats pushes, and the first value of each event per monitor wins (kept event by event, so `avgPing` and the uptimes may come from different `sendStats` runs) because `sendStats` re-emits on every heartbeat
    - each row `{ id, name, uptime24h, uptime30d, avgPing, certExpiresAt, certDaysRemaining }`: `uptime24h` / `uptime30d` are Kuma's 0–1 ratios over its 24-hour and 30-day (720-hour) windows — the two versions compute them differently (1.x duration-weighted, 2.x count-based buckets where MAINTENANCE is excluded and PENDING counts as down), so a ratio is only comparable within one server version; `avgPing` is the 24-hour average ping: on 1.x `parseInt(AVG(ping))`, NaN and carried as null when no beat in the window has a ping; on 2.x a two-decimal average weighted by UP counts, null when there is no UP beat and also when the average is exactly 0
    - `certExpiresAt` is `certInfo.validTo` as ISO 8601 and `certDaysRemaining` is `certInfo.daysRemaining` from the parsed `info_json`; both null when the monitor has no `monitor_tls_info` row or the JSON is malformed. They are the values stored at the monitor's last TLS check, so `certDaysRemaining` does not count down while a monitor is paused. A monitor that has never been checked prints `uptime24h` / `uptime30d` 0 and `avgPing` null, which looks the same as a monitor that was down the whole window
    - on 2.x the row gains `uptime1y`, the 0–1 ratio over the one-year window — a third `uptime` period `"1y"` 2.x `sendStats` pushes right after the 30-day one since 2.0.0. The key is absent rather than null when the server never sent it, so a 1.x row keeps its shape
    - on 2.1.0+ the row can gain `domainExpiresAt` / `domainDaysRemaining` from `domainInfo` (`domain_expiry.expiry` as ISO 8601 and `daysRemaining`), pushed right after `certInfo` and only for a monitor whose domain resolved an expiry through RDAP — the keys are absent when the event never came; when it came with an unusable field the keys stay and that field is null like a malformed `certInfo`, and only a datetime with an explicit `Z` or offset parses at all — an offset-less value would read as local time and shift the instant
    - certInfo wait: inside a monitor's stats burst `certInfo` follows `uptime` 720 directly, but heartbeat-triggered `sendStats` runs interleave with the post-login walk, so another monitor's pushes say nothing about this one's certificate. Each requested monitor's `certInfo` wait ends 500 ms after its own `uptime` 720; a `certInfo` that has arrived by then is used, otherwise the cert fields are null. A missing certificate never makes the command fail. The 500 ms is a client-side bound, per monitor and independent of what else the command waits for (the measured gap between `uptime` 720 and `certInfo` is about 1 ms on 1.x, which runs its DB queries one at a time — a heavily loaded instance could stretch it; on 2.x the stats come from an in-memory calculator computed concurrently and only the certInfo read touches the DB), so a `certInfo` slower than that reads as null with exit 0; a `certInfo` that has arrived ends that monitor's wait at once — on a server that cannot emit `domainInfo`; on 2.1.0+ a landed `certInfo` instead holds the wait for a 200 ms tail grace, because upstream's sendStats awaits a monitor row read plus the `domain_expiry` lookup between the cert and domain emits — ending on `certInfo` would drop a domain push that lands ms later, while holding the whole bound would charge every monitor without a resolvable domain expiry (the common case) 500 ms for an event that cannot come — and a `domainInfo` that lands ends the wait as the burst's last emit. Because the values are kept event by event, one may come from a heartbeat-triggered run computed just before Kuma stored that beat, one beat behind what the dashboard settles on — a monitor whose first-ever beat lands in that window can print `avgPing` null
- `monitors add --type <group|http|port|ping|keyword|json-query|grpc-keyword|dns|docker|real-browser|push|steam|gamedig|mqtt|kafka-producer|sqlserver|postgres|mysql|mongodb|radius|redis|tailscale-ping|system-service|pm2|websocket-upgrade|sftp|manual|ntp|rabbitmq|smtp|snmp|oracledb|globalping> --name <name> [options]` (the 1.23 picker order of EditMonitor.vue with the 2.x-only types `system-service`, `pm2`, `websocket-upgrade`, `sftp`, `manual`, `ntp`, `rabbitmq`, `smtp`, `snmp`, `oracledb` and `globalping` appended; a 2.x-only type exits 2 after `connect()` when the server reports 1.x like a 2.x-only field, `type "<type>" needs Uptime Kuma 2.x` — 1.23 would store the row and every check would throw "Unknown Monitor Type". A type that shipped mid-line carries its first release as the minimum instead: `websocket-upgrade` exists only from 2.1.0 (upstream #5613), `system-service` only from 2.1.0 (#6488), `pm2` and `ntp` only from 2.5.0 (#7114 / #7214), `sftp` only from 2.5.4 (#7034), `oracledb` only from 2.3.0 (#7156) and `globalping` only from 2.1.0, so on an older 2.x each exits 2 with `type "<type>" needs Uptime Kuma >= <release>; the server reports <version>` — the same refusal, a minor line higher)
    - options: `--url`, `--hostname`, `--port`, `--keyword`, `--invert-keyword`, `--json-path`, `--json-path-operator`, `--expected-value`, `--packet-size`, `--dns-resolve-server`, `--dns-resolve-type`, `--docker-container`, `--docker-host`, `--game`, `--grpc-url`, `--grpc-service-name`, `--grpc-method`, `--grpc-protobuf <file>`, `--grpc-enable-tls`, `--mqtt-topic`, `--mqtt-username`, `--mqtt-success-message`, `--kafka-producer-broker <host:port>` (repeatable), `--kafka-producer-topic`, `--kafka-producer-message`, `--kafka-producer-ssl`, `--kafka-producer-allow-auto-topic-creation`, `--rabbitmq-node <url>` (repeatable), `--rabbitmq-username <username>`, `--radius-username`, `--radius-called-station-id`, `--radius-calling-station-id`, `--snmp-oid <oid>`, `--snmp-version <version>`, `--snmp-v3-username <username>`, `--system-service-name <name>`, `--ssh-username <username>`, `--ssh-auth-method <method>` (the picker's two select values `password` / `privateKey`, first the default), `--sftp-path <path>`, `--subtype <ping|http|dns>` (globalping), `--location <location>` (globalping), `--protocol <protocol>` (globalping — the picker's options differ per subtype: ICMP/TCP for ping, unset/HTTP2 for http, UDP/TCP for dns), `--ip-family <ipv4|ipv6>` (the picker's Ip Family select shows on http / keyword / json-query / grpc-keyword and every globalping subtype — unset is its auto-select; a 2.x-only field, so on a 1.x server it exits 2 after `connect()` like any other), `--database-query <sql>`, `--interval <s>` (60), `--retry-interval <s>`, `--max-retries <n>` (0), `--resend-interval <n>` (0), `--timeout <s>` (non-negative; the timing rule is below), `--proxy-id <id>`, `--notification-id <id|name>` (repeatable), `--notifications-from <monitorId|name>`, `--parent <groupId|name>`, `--paused`, `--push-token <token>`, `--tag <tagId[:value]>` (repeatable), `--set <key>=<value>` (repeatable), `--config-file <json>`
    - required per type: http / keyword / json-query / real-browser need a url — `--url` or a `url` key in `--set` / `--config-file` (a credential-bearing url only fits `--config-file`, so the check runs on the merged value); websocket-upgrade needs a url limited to `ws://` / `wss://` — and on 2.x every url type's merged url is checked against submit()'s acceptList (2.5.11 EditMonitor.vue:4267-4292): `http:` / `https:` for http / keyword / json-query, `ws:` / `wss:` for websocket-upgrade, any parseable scheme for real-browser, each with a non-empty host (`Monitor.validate` does not recheck it, so a stored off-scheme url would only surface as a check that can never connect; the UI's stricter `wss?://.+` input pattern is cosmetic — the submit gate accepts `ws:foo`, which parses to host `foo` and dials like `ws://foo`, so the CLI mirrors submit rather than the pattern; 1.23's submit has no such gate, so the check is 2.x-only) — a `ws://` / `wss://` url can still carry userinfo, so the credential scan below applies to it too, and a refused url is echoed redacted — a fragment is refused on top of submit()'s gate because `ws` throws `SyntaxError: The URL contains a fragment identifier` before connecting (an http client just drops one);     - `docker_host` and `proxyId` are checked against the pushed `dockerHostList` / `proxyList` when the edit sets them (see the shared validation note below)
    - for a push monitor a `pushToken` the edit sets must be a non-empty string — anything else exits 2 before `editMonitor` is sent
    - the version-specific timing rules apply only to values the edit sets, like the other edit validation — a stored out-of-range `interval` or `timeout: 0` goes back untouched. `retryInterval` / `timeout` derive from the interval only when the edit touches `interval` or `timeout`; a stored `timeout: 0` is otherwise sent back untouched even though Kuma 1.23.17 runs it as interval × 800 seconds on HTTP checks. The UI's interval watcher moves `retryInterval` only while the two stored values were equal — edit does the same: an `interval` set without `retryInterval` carries the stored equal `retryInterval` along, while a stored one that differed, or one the same edit sets, is kept. The UI may legitimately store `timeout: 0`, a deleted docker host as `docker_host: null`, `proxyId: 0` or `port: 0`
    - a `type` change keeps the stored fields the new type shares: editing a `radius` monitor to `mysql` keeps the stored `radiusPassword`, which Kuma 1.23.17 reads as the MySQL password — the UI stores both in that one field. Two stored values do not follow a type change: a missing `timeout` becomes the new type's default, and so does a nonpositive one on 1.x — where Kuma reads 0 as interval × 800 seconds — while a stored `0` is kept on 2.x where Kuma accepts it (unless the same edit sets `timeout`), and `httpBodyEncoding` becomes null when the new type is outside http / keyword / json-query (unless the edit sets it), like the UI's `submit()` on both versions. On Kuma 2.x a type change also resets a stored watcher-default `timeout` — the per-type picks (1 / 5 / 10) or the generic 48 — to the new type's pick like the 2.x watcher does, while a custom timeout is kept; on 1.x the watcher never touches `timeout`, so even a stored 48 is the user's pick and survives. One consequence is the 2.x ping rule applies to the reset value: a stored `ping_per_request_timeout` that outgrows the new type's default exits 2 the way the server's `Monitor.validate` would refuse the UI's same save
    - prints the monitor as Kuma saved it (fetched again with `getMonitor`), redacted and with `tags` normalized as in `monitors get`; fields Kuma's `editMonitor` does not copy (such as `active`, which the command refuses in `--set` / `--config-file` for that reason) keep their stored value, and the re-read shows it. The save already happened, so a failed re-read degrades like `settings set`: the sent object is printed redacted plus a stderr warning and exit 0 — an exit-70 unexpected shape stays loud
- `add` and `edit` both run `validateFinalMonitor` on the merged monitor right before sending, but with different scope. On `add` the whole monitor is judged: the per-type required fields must be present (`url`, `keyword`, `jsonPath` + `expectedValue`, `grpcUrl` + `grpcServiceName` + `grpcMethod` + `grpcProtobuf` for grpc-keyword, `hostname`, `port`, `mqttTopic`, `kafkaProducerTopic` + `kafkaProducerMessage` + a non-empty `kafkaProducerBrokers`, the five `radius*` fields including the secret `radiusPassword` / `radiusSecret`, `game`, `docker_container` + `docker_host`, `pushToken`, `databaseConnectionString` for sqlserver / postgres / mysql / mongodb / redis / oracledb, `basic_auth_user` + `basic_auth_pass` for oracledb, `system_service_name` for system-service / pm2, `sshUsername` and the credential `sshAuthMethod` selects (`sshPassword` for `password`, `sshPrivateKey` for `privateKey`) for sftp, a non-empty `rabbitmqNodes` of `http://` / `https://` URLs plus `rabbitmqUsername` and `rabbitmqPassword` for rabbitmq, and `dns_resolve_server` for `dns`, and for globalping the subtype-conditional set — `hostname` for ping / dns, an http(s) `url` for http, `port` always for dns and for ping under TCP, plus `subtype` / `location` / `protocol` validated against the picker's per-subtype options and `dns_resolve_type` against globalping's wider RR list), `parent` must be null or an existing group, and `docker_host` / `proxyId` must name ids in the pushed `dockerHostList` / `proxyList`. On `edit` only the fields the edit sets are judged the same way, plus every required field of the new type when `type` changes — a stored value the edit does not touch is never re-judged. A hatch `type` on edit must be one of the types the pickers of both versions offer; anything else exits 2, and a 2.x-only type exits 2 after `connect()` when the server reports 1.x
- `monitors pause <id|name>` / `monitors resume <id|name>`: prints `{ id, active }`
- `monitors delete <id|name> --yes [--children]`: sends `deleteMonitor` and prints `{ id, deleted: true }`; without `--yes` exits 2 before connecting. The id is checked against the pushed `monitorList` first because Kuma 1.23 answers ok even for an unknown id. The monitor's `monitor_tag` rows are deleted with it (foreign key cascade). Deleting a group monitor does not delete its children: their `parent` becomes null (Kuma 1.23 `ON DELETE SET NULL`), so they become top-level monitors and keep their own active / paused state, and the monitor's heartbeats are deleted with it. On 2.1.0+ `--children` sends `deleteChildren` and deletes the group's whole subtree instead (`deleteMonitorRecursively`); 2.x keeps the unlink behaviour by default, so sending the id alone hits its old-argument shim. On an older server `--children` exits 2 with `--children needs Uptime Kuma >= 2.1.0` — 1.x would read the boolean second argument as the callback
- `monitors clear-beats <id|name> --yes`: sends `clearHeartbeats`, which DELETEs the monitor's heartbeat rows, and prints `{ id, cleared: "beats" }`; without `--yes` exits 2 before connecting. The id is checked against the pushed `monitorList` first because the event answers ok even for an unknown id; other monitors' beats are untouched (on 2.x the stat tables are cleared and an active monitor restarts)
- `monitors clear-events <id|name> --yes`: sends `clearEvents`, which resets `msg` and `important` on the monitor's heartbeat rows — `events` then shows nothing while `beats` keeps the rows — and prints `{ id, cleared: "events" }`; same `--yes` and unknown-id rules (on 2.x the importantHeartbeatList re-push does not happen)
- `monitors tag <id|name> --tag <tagId> [--value <value>]`: attaches the tag; `--value` defaults to `""` (never sent as null). The monitor must be in the pushed `monitorList` and the tag in `getTags` — exit 1 each. `addMonitorTag` has no unique constraint, but the same tag+value already attached prints `{ id, tagId, value, skipped: true }` and exits 3 without sending. Otherwise sends `addMonitorTag` and prints `{ id, tagId, value }`
- `monitors untag <id|name> --tag <tagId> [--value <value>]`: `--value` defaults to `""`; the monitor must have that exact tag+value in the pushed list, else exit 1 — `deleteMonitorTag` answers ok even when nothing matches. A stored null value can never match `value = ?`, so removing one exits 1 with a message saying Kuma cannot remove a tag whose value is null through this event. Prints `{ id, tagId, value, removed: true }`
- `monitors retag <id|name> --tag <tagId> --value <value>`: the monitor must have the tag (exit 1); sends `editMonitorTag`, which sets the value on EVERY attachment of that tag on the monitor and answers ok even when nothing matches. A monitor that has the tag attached more than once exits 1 before sending — use `untag` + `tag` instead, since retagging would collapse the rows into identical duplicates. Prints `{ id, tagId, value }`
- none of `addMonitorTag` / `editMonitorTag` / `deleteMonitorTag` pushes `monitorList` again; each command logs in once, so the next run sees the new state

### maintenance

- maintenance windows come from the pushed `maintenanceList`; every command checks the id against it before requesting because `getMaintenance` of an unknown id dies inside `toJSON` rather than answering cleanly
- `maintenance list`: array sorted by id of `{ id, title, strategy, active, status }`; `status` is Kuma's computed value (`inactive`, `scheduled`, `under-maintenance`, `ended`, `unknown`)
- `maintenance get <id>`: the `getMaintenance` object; unknown id exits 1
- `maintenance add --title <t> --strategy <s> [--description d] [--start <ISO> --end <ISO>] [--timezone <tz>] [--paused] [--config-file <json>]`
    - `--strategy` is one of `manual`, `single`, `cron`, `recurring-interval`, `recurring-weekday`, `recurring-day-of-month`
    - the payload starts from the UI's `isAdd` defaults (`cron: "30 3 * * *"`, `durationMinutes: 60`, `intervalDay: 1` — the UI caps it at 3650 and so does the CLI on 2.x (on 1.x `recurring-interval` caps at 31, see below) — `timeRange` 02:00–03:00, empty `weekdays` / `daysOfMonth`, `dateRange: []`, `active: true`); `dateRange` is always an array because `jsonToBean` indexes `dateRange[0]` unconditionally. One default differs on purpose on 1.x: its UI sends `timezoneOption: null` where the CLI sends `"SAME_AS_SERVER"` — same effect, the server timezone (the 2.x UI's default is `SAME_AS_SERVER` itself, so the CLI matches it there)
    - `--start` / `--end` are the UI's "Effective Date Range" and take local ISO 8601 datetimes without an offset (`Z` and `±hh:mm` exit 2 — Kuma reads the strings as local time in `timezoneOption`, so an offset would be misparsed). The datetime must be a real calendar date — the day must exist in its month (leap years included) and hour/minute/second stay in range, so `2031-02-31` and `T24:00` exit 2 like the UI's datetime-local never producing them. Every strategy except `manual` accepts them, `single` requires both (end after start), and on 2.x a cron/recurring range carrying both ends is order-checked the same way (Kuma stores an inverted range without complaint and the window would never run); the UI allows a start without an end so `--start` alone sends `[start]` — exit 2 before connecting on a violation. Whether `single` needs the range is judged on the merged strategy and `dateRange`, so a `--config-file` `strategy` or `dateRange` decides it too. `cron` and the `recurring-*` strategies take a start but never an end on 1.x: Kuma 1.23.17's `Maintenance.run` leaves `duration` undefined when `end_date` is set and the remaining time is >= duration, so `setTimeout(..., undefined)` ends the window immediately — the CLI refuses an end date for them on a 1.x server (exit 2 after connect, once the version is known). On 2.x `inferDuration` falls back to `duration * 1000` and the end date is accepted
    - `--timezone` takes an IANA name or `SAME_AS_SERVER`; an invalid name exits 2 because `dayjs.tz` throws inside `toJSON` and would break the `maintenanceList` push for every client
    - `--config-file` is merged after the typed flags and carries the schedule fields of the other strategies: `cron` needs `cron` — a croner nickname (`@yearly`, `@annually`, `@monthly`, `@weekly`, `@daily`, `@hourly`) or a 5 or 6 whitespace-separated field expression in croner's shape: the first `L` is stripped from day-of-month and day-of-week, month and day-of-week parts of 3+ chars may use the JAN-DEC / SUN-SAT names (converted to numbers), the first `?` of each part is croner syntax for the field's current value, judged by substituting every value the clock can produce and running the same per-entry verdict as a literal (`?*`, `5*?` or `1-5*?` pass, since parseInt ignores the trailing characters; `5-?` or `?-5` outside the field's top bound flip with the clock and are refused) — and since `?` may sit inside a larger number, a substitution can also land the whole field on dead: `?0/5` steps from `60` on most minutes, so it is refused in seconds/minutes/hours where nothing can rescue it, kept when a comma sibling stays live (`?0/5,0`), and in day-of-week joins the joint date-field check like a static dead field (`0 0 * * ?0/5` is refused while `0 0 15 * ?0/5` still runs on the 15th), and what remains may only contain `[0-9*/,-]` — on 2.x the day-of-week part additionally allows `#` and `L`, croner 8's nth-weekday and last-weekday forms like `0 9 * * 5#3`; an empty part (surrounding whitespace) is refused too — croner 6 parses it into a schedule that never runs and croner 8 throws — and `durationMinutes` (positive integer); every `recurring-*` needs `timeRange` (two `{hours, minutes, seconds?}` objects with seconds in 0–59), `weekdays` (integers 0–6), `daysOfMonth` (integers 1–31 or `"lastDay1"`) and `intervalDay` (positive integer up to 3650 — for `recurring-interval` the cap is 31 on 1.x because `generateCron` emits `*/N` in day-of-month and croner 6 rejects a step over 31, while 2.x generates a plain daily cron and allows the UI's 3650 — with an upstream quirk: 2.x's re-run gate compares against a timestamp frozen at `run()`, so `intervalDay` ≥ 2 fires once per boot/add/edit/resume cycle, see `docs/design/kuma2.md`); `recurring-weekday` additionally needs a non-empty `weekdays` and `recurring-day-of-month` a non-empty `daysOfMonth`, because `generateCron` joins them into the cron expression. A missing or malformed field exits 2 before connecting instead of failing inside Kuma; the rules that differ between versions — the cron/recurring end-date refusal, the `recurring-interval` cap of 31 and the narrower cron grammar — are checked after connect on a 1.x server (the pre-connect check applies the union of both versions' rules). The cron check also mirrors croner's value rules, not just its shape: every comma entry is checked against the field's value range (seconds/minutes 0–59, hours 0–23, day-of-month 1–31, month 1–12, day-of-week 0–7 — named months and weekdays are converted to numbers first), a range's bounds must be in range with the lower not above the upper, a step of 0 is refused, and a step is capped by the field's bitmap length (day-of-week: 8 on 1.x, 7 on 2.x — so `*/8` is 1.x-only); numeric bounds are read the way both croners' `parseInt` reads them — charset characters after the digits are ignored, so `1-28*` schedules as `1-28` and `5*3` as `5` — while a range-with-stepping keeps its strict `x-y/N` shape and `1-28/2*3` is refused. On 2.x croner only checks the values a range-with-stepping actually lands on, so `20-33/7` is allowed on 2.x but refused on 1.x, which checks both bounds. A step start past the bitmap — or an empty `/N` — is legal to both croners but contributes no values: croner 6 iterates from the raw start so any index below the bitmap length schedules, while croner 8 offsets it by the field minimum (a day-of-month or month start of 0 throws on 2.x but parses on 1.x). A field where every comma entry is dead like that never runs — and an all-zero month loops `nextRun()` forever, blocking the Kuma event loop — so it is refused; a dead entry next to a live one still goes through, matching what the server schedules. The two date fields are judged jointly because croner matches day-of-month and day-of-week with an OR when both are restricted: a dead day-of-month is refused only when day-of-week is `*` or all-dead too (`0 0 32/5 * 1` still runs Mondays), and a dead day-of-week only when day-of-month is `*` or all-dead. When day-of-week cannot rescue, the day-of-month × month pair must also leave a real date — `0 0 31 2 *` and `0 0 30 2 *` never run (February counts its leap day, so `0 0 29 2 *` passes) and are refused. A day-of-month or month part carrying `?` is judged under every possible current value, compound entries included — `0 0 31 ? *` dies in February, `0 0 ? 4 *` on the 31st, `0 0 ?,31 2 *` on the 30th — and when both fields carry one they take the same "today", so `0 0 ? ? *` always names a real date while `0 0 31 ?,4 *` is refused. On croner 6 a day-of-month or month `x/N` counts raw bitmap indexes, shifting the hits one value up (`2/12` in month lands on March, so `0 0 31 2/12 *` schedules on 1.x and `0 0 30 1/12 *` is 2.x-only). A stripped day-of-week `L` leaves a dead field on 1.x, which the same joint check judges: `0 0 1 * L` runs on the 1st through OR matching, `0 0 * * L` never runs and is refused. This matters because Kuma 1.23.17 calls the async `validateCron` without await, so even a bad expression is stored and the rejection goes unhandled — the window is saved but never runs; 2.x's synchronous `validateCron` answers `ok:false` for a bad value. The defaults already satisfy `cron` and `recurring-interval`, so those two need no config file
    - `--config-file` cannot set `id`; same title already present (exact match) prints `{ id, title, skipped: true }` and exits 3 without sending `addMaintenance`
    - prints `{ id, title, strategy, active }`
- `maintenance edit <id> [--title t] [--description d] [--start --end] [--timezone tz] [--set k=v]... [--config-file <json>]`
    - `editMaintenance` runs `jsonToBean` over the whole object, so the CLI fetches the maintenance, merges and sends it back; at least one change is required (exit 2 before connecting)
    - `--start` and `--end` each patch one end of the stored `dateRange` — `--start` replaces index 0, `--end` index 1 — so either may be given alone (`--end` alone needs a stored start, exit 2 otherwise); on add `--end` still requires `--start`, and `manual` takes neither flag on either command. On 1.x the cron/recurring end-date refusal applies to the merged range too — `edit --end` exits 2, and a strategy change to `cron`/`recurring-*` fails the same way when the stored range has an end (`single` → `cron` included); the error says to drop the end, and for a stored one suggests `--set 'dateRange=["<start>"]'` (quoted for the shell) in local time. On 2.x the end date is accepted. Untouched `dateRange` values are not re-judged, so a `--title` edit on a window that already has an end still passes
    - precedence: fetched < `--config-file` < `--set` < typed flags; `id` is refused in `--set` and `--config-file`, and a `strategy` that is not one of the six exits 2 before connecting (the merged-value check still runs after the fetch). A `cron` given through `--set` or `--config-file` exits 2 on the union check before connecting, like add — unless the same edit names a non-`cron` strategy where the value is inert, and a non-string value is left for the post-fetch check that knows the merged strategy. The versioned check still judges the merged cron after the fetch. The strategy rules (manual takes no range, single needs both, cron/recurring take no end on 1.x) judge the merged strategy, so a hatch can flip them — e.g. `--set strategy=manual` makes `--start` invalid even on a cron window
    - the same field validation as add runs on the merged object, scoped like `monitors edit`: only touched keys are judged, plus every field the new strategy requires when `strategy` changes — a `--title` edit on a cron maintenance does not re-judge its cron fields. `dateRange` is judged only on the final merged value, so a `--set` can repair a bad `--config-file` range; its entries must be offset-free local ISO datetimes like the flags
    - prints the maintenance as Kuma saved it
- `maintenance pause <id>` / `maintenance resume <id>`: prints `{ id, active }`
- `maintenance delete <id> --yes`: sends `deleteMaintenance`, prints `{ id, deleted: true }`; without `--yes` exits 2 before connecting; unknown id exits 1 because the delete answers ok even for unknown ids
- `maintenance monitors <id>` and `maintenance status-pages <id>` show or change what a maintenance affects: `[{ id, name }]` for monitors, `[{ id, title }]` for status pages, sorted by id
    - `--add <id>` / `--remove <id>` (repeatable) read the current set (`getMonitorMaintenance` / `getMaintenanceStatusPage`), apply the change locally and send the full set; `--set-ids <id,...>` replaces it exactly (`--set-ids ""` clears it) and cannot be combined with `--add` / `--remove` (exit 2); the value is trimmed, split on commas and each element trimmed again before name resolution, so a monitor name containing a comma cannot be used here — give its id. On `maintenance monitors` the targets may be monitor names like every other monitor id; on `maintenance status-pages` they stay ids and keep their pre-connect validation. Reading then sending back means a change made in the UI between the read and the write is overwritten — Kuma 1.23 has no compare-and-swap for these sets, so there is no way to prevent it
    - every supplied id must exist in the pushed `monitorList` / `statusPageList` — exit 1 — and the maintenance id is checked against `maintenanceList` first
    - the `add*` events DELETE every row the maintenance has and INSERT the sent ids: they replace the whole set, they do not add. That is why `--add` reads the current set first — sending only the new id would wipe the rest. After a successful write an id that is no longer in the pushed list prints with a `null` name / title instead of failing the command

### status-pages

- status pages come from the pushed `statusPageList` (`StatusPage.toJSON` values keyed by id); every command checks the slug against it before requesting. `unpinIncident` answers ok even for an unknown slug (the UPDATE runs with a NULL page id), while `getStatusPage` / `deleteStatusPage` / `postIncident` answer ok:false — the pre-check gives the CLI's own `status page <slug> not found` either way
- `status-pages list`: the pushed pages as an array sorted by title like Kuma's `ORDER BY title` (the pushed object's numeric keys would enumerate by id, so the title order is restored client-side)
- `status-pages get <slug>`: `getStatusPage`'s `config` merged with `publicGroupList` and the incident(s) from `GET <url>/api/status-page/<slug>` — no auth — printed as `{ ...config, publicGroupList, incident, incidents }`. On 1.x the route's `incident` (one object or null) is printed as `incident` and `incidents` is `[incident]` or `[]`; on 2.x the route's `incidents` array (every pinned and active incident, `created_date` DESC) is printed as `incidents` and `incident` is its newest pinned one by `createdDate` — an undated incident never beats a dated one, a tied `createdDate` goes to the higher id (the route's `ORDER BY created_date DESC` does not order ties) and missing dates fall back to the last element — so output written for 1.x keeps working; `incident` is null when none. A body without the expected key exits 70. The route is cached 5 minutes by Kuma (apicache) keyed on the full URL including the query string; `saveStatusPage` and `deleteMonitor` clear it on both versions and `deleteStatusPage` clears it on 2.x only, while `addStatusPage`, `postIncident` and `unpinIncident` clear it on neither — so the CLI adds a unique `?_=<nonce>` query to every read and Kuma's cache never answers it (a reverse proxy that ignores query strings could still serve a stale body). Each such read leaves one entry in Kuma's in-memory apicache for 5 minutes (about 1–2 KB for a small page; `get` adds one, `save` two), the same an anonymous client can already cause on this public route. A network error or timeout on that fetch exits 2 and a non-200 answer exits 1, both naming the URL
- `status-pages add --slug <s> --title <t>`: validates like Kuma before connecting — title trimmed non-empty, slug trimmed, lower-cased and matching `^[a-z0-9]+(?:-[a-z0-9]+)*$` (exit 2). A slug already in `statusPageList` prints `{ id, slug, title, skipped: true }` and exits 3 without sending — `status_page.slug` also has a UNIQUE index. `addStatusPage` answers only `{ ok, msg }` and does not re-push the list, so the new page's `toJSON` is read back with `getStatusPage`
- `status-pages save <slug> --config-file <path>`: the file is a JSON object validated before connecting (exit 2). Allowed keys are `slug`, `title`, `description`, `theme` (`auto` / `light` / `dark`), `showTags`, `footerText`, `customCSS`, `showPoweredBy`, `showCertificateExpiry`, `googleAnalyticsId`, `autoRefreshInterval`, `rssTitle`, `showOnlyLastHeartbeat`, `analyticsId`, `analyticsScriptUrl`, `analyticsType`, `domainNameList`, `logo`, `publicGroupList`; anything else — `id`, `icon`, `published` included — is refused by name. The key set is the union of both Kuma versions: `autoRefreshInterval` (non-negative integer), `rssTitle` / `analyticsId` / `analyticsScriptUrl` (string or null), `showOnlyLastHeartbeat` (boolean) and `analyticsType` (`google` / `umami` / `plausible` / `matomo` / `rybbit` or null) are validated before connecting, and once connected the six 2.x-only keys exit 2 on a 1.x server while `googleAnalyticsId` exits 2 on a 2.x server pointing at `analyticsId` / `analyticsType`. `slug` is trimmed and lower-cased like the UI's save. Groups keep only `{ id?, name, monitorList: [{ id, sendUrl? }] }` (`sendUrl` also accepts the 0/1 the public JSON emits) and extra keys a `get` output carries — `weight`, `type`, `url`, `tags` — are allowed and ignored, so a `get` result's `publicGroupList` feeds back unchanged; a file `url` is dropped rather than sent — the public `url` cannot be sent back safely (it may be the password-redacted `***` form, and the public JSON does not say whether it is the custom URL or the monitor's own) and 2.x's `saveStatusPage` would store whatever is sent as the group's `custom_url`
- the save fetches the page like `get` does — the public-route read carries the same cache-busting query, so it never sees a body cached before a delete/re-add — and sends `saveStatusPage` the fetched `toJSON` with the file merged over it — a key the handler reads but the merge lacks would be stored as null — plus the file's `publicGroupList` or, when absent, the fetched groups reduced the same way. On 2.x the fetched-group reduction keeps one more field: the public monitor `url` — `custom_url ??` the monitor's own url, emitted only when `sendUrl` is on — goes back only when it differs from the monitor's own `url`, because `saveStatusPage` rewrites `monitor_group` wholesale and stores a sent `url` as `custom_url`; the difference marks a custom URL set in the UI, so a `save` that only changes the title no longer wipes it. The pre-save public read is unredacted for this comparison and the value is sent verbatim, but it is never printed — every printed group list redacts a password in a url to `***`. A public url equal to the monitor's own sends no `url` (sending it would pin the monitor url as a custom one, and a custom url equal to the monitor url is publicly indistinguishable anyway — though only at save time: the UI pins the public url as `custom_url` on every save, so after a monitor url change a UI-saved page keeps showing the old url while a CLI-saved one follows the new); a `sendUrl`-off monitor carries no public url, so a custom URL on it cannot be detected and is cleared — the UI cannot preserve it either. A file's own `publicGroupList` keeps the `{ id, sendUrl }` shape and cannot express custom URLs. `logo` is the `imgDataUrl` argument (a `data:` URL must be `data:image/png;base64,`) and defaults to the fetched `icon`, like the UI; an empty stored icon reads as `/icon.svg` (the UI behaves the same). A `domainNameList` entry is moved off any other page that had it. A file `slug` renaming onto another page's slug prints `{ id, slug, title, skipped: true }` and exits 3; a group `id` that is not a current public group of the page or a monitor `id` missing from `monitorList` exits 1 before saving — an unknown group id would make Kuma's `findOne` return null and throw after the page row was already stored. Groups are replaced wholesale: an entry without `id` is created (Kuma assigns the id), one with an `id` is updated, and every group not listed is deleted. It then prints like `get` under the new slug when it changed; if that read-back fails the save already happened, so the sent config is printed with the save response's `publicGroupList` (it carries the assigned group ids), `incident` null and `incidents` `[]`, a one-line warning naming the failure goes to stderr and the exit code stays 0. That degraded stdout is not a fresh read: `incident` null / `incidents` `[]` means unknown, the groups are in the reduced save shape, and `icon` is the pre-save one even when the file set `logo`; a script that needs the stored state reads it again with `get`. An unexpected response shape on the read-back (exit 70) is not degraded and still exits 70
- `status-pages delete <slug> --yes`: without `--yes` exits 2 before connecting; unknown slug exits 1 (Kuma's own answer is ok:false "Status Page is not found"). The page's incidents and groups are deleted with it. Prints `{ slug, deleted: true }`
- `status-pages incident <slug> --title <t> --content <c> [--style <s>]`: `--style` is one of `info`, `warning`, `danger`, `primary`, `light`, `dark`, default `primary` (the StatusPage.vue `createIncident` default); title and content must be non-empty (exit 2). On 1.x `postIncident` unpins every previous incident of the page itself; on 2.x it does not, so the CLI calls `unpinIncident` first — either way only the new incident stays pinned (the two calls are not atomic: if `postIncident` fails after the unpin the page may be left with no pinned incident — a timed-out post can still have landed — on 2.x the error says the incidents were unpinned first, and re-running the command restores one). Prints the returned `incident` (`Incident.toPublicJSON`)
- `status-pages unpin <slug>`: prints `{ slug, unpinned: true }`
- `status-pages incident-history <slug>` (2.1.0+): follows `getIncidentHistory`'s `nextCursor` until `hasMore` is false and prints `{ slug, total, incidents }` — the whole history `created_date` DESC, not one page. On an older server exits 2 with `incident-history needs Uptime Kuma >= 2.1.0`. A non-array `incidents`, a non-integer or negative `total`, a non-object row or one without a positive-integer `id`, or `hasMore` without a usable `nextCursor` exits 70; a `nextCursor` the walk already visited — an immediate repeat or a cycle — stops the walk rather than re-requesting forever; a page's rows are still collected but deduped by id, so a replay contributes nothing to the count while new rows a cycling server delivered are kept. Rows sharing a page boundary's `created_date` are unreachable through the server's `<` cursor, so a fetched count below `total` prints a `may be incomplete` warning — a protocol limit, detected rather than hidden; a count above `total` (a concurrent post between pages) is not the shortfall and does not warn, while a walk the cursor stalled with the count matching `total` warns `stopped early` — `hasMore` was still true, and a server that cannot continue its own walk can miscount too
- `status-pages incident-edit <slug> <id> [--title <t>] [--content <c>] [--style <s>] [--pin|--unpin]` (2.1.0+): `editIncident` overwrites every field unconditionally like the UI's pre-filled form, so the stored incident is fetched through `getIncidentHistory` first (stopping at the page that holds the id) and the flags merge over it — an omitted flag keeps its stored value. A flag-less call exits 2 before connecting like the other edit commands, as does an invalid id, an empty `--title` / `--content` flag, and a `--pin` / `--unpin` pair; a malformed stored title or content exits 70 like a non-object row. An unknown id exits 1 `incident <id> not found` — or `incident <id> may exist` when the walk came back `incomplete` (a count below `total`, the same `created_date` boundary loss as `incident-history`) or `stopped early` (a repeated cursor), since the id could sit beyond the cursor. An unset stored `pin` sends `pin: true` like the UI's default, and a non-string stored `style` falls back to `warning` like `validateIncident`. Prints the returned `incident`
- `status-pages incident-resolve <slug> <id>` (2.1.0+): sends `resolveIncident`, which marks the incident inactive and unpinned; prints the returned `incident`. An invalid id exits 2 before connecting, an unknown id exits 1 with Kuma's `Incident not found or access denied`

### settings

- `settings get`: the `getSettings` `data` object as stored; `steamAPIKey` and `globalpingApiToken` print as `"***"` when non-empty and userinfo inside `primaryBaseURL` (`https://user:pass@host/`) prints as `***` like a monitor url
- the `get` output is not a valid `--config-file` as is when it carries masked values: `steamAPIKey` and `globalpingApiToken` read `"***"` and userinfo inside `primaryBaseURL` reads `***` — `set` refuses all three with exit 2 (feeding them back would store the mask as the secret) and the message says to omit the key or give the real value (for `primaryBaseURL` the whole real URL, through `--config-file`). A stored key outside the editable list is not rejected: `set` fetches the stored object and sends it back whole, so keys the input does not name — including ones only another Kuma version edits — round-trip untouched. Copy only the keys being changed
- `settings set [--set <key>=<value>]... [--config-file <json>]`: at least one of the two (exit 2). The allowed keys are the union of what the settings components edit on each supported version — on 1.x: `serverTimezone`, `searchEngineIndex`, `entryPage`, `primaryBaseURL`, `steamAPIKey`, `nscd`, `dnsCache`, `chromeExecutable`, `checkUpdate`, `checkBeta`, `trustProxy`, `keepDataPeriodDays`, `tlsExpiryNotifyDays`, `disableAuth`; on 2.x the same minus `dnsCache` plus `domainExpiryNotifyDays` and `globalpingApiToken`. An unknown key exits 2 naming it and its source before connecting; a key that only the other version edits passes that check and is refused after connect with exit 2 naming the version (`"dnsCache" is not read on Uptime Kuma 2.x` / `"domainExpiryNotifyDays" needs Uptime Kuma 2.x; the server reports 1.23.17`, or `the server sent no version, so 1.x was assumed`), before `getSettings` is even read
- every value is validated before connecting against the UI's type and bounds: the seven booleans must be booleans; `serverTimezone` must be one of the names in `src/timezones.ts`, compared case-sensitively — before connecting the union of both versions' lists, after connecting the connected version's own list (a name only the other version offers, like `America/Nuuk` on 1.x or `America/Rainy_River` on 2.x, exits 2 then). Each list is `"UTC"` plus the names that version's UI offers that its `checkTimezone` accepts — 1.x: the `timezones-list` 3.0.3 names measured by running `dayjs.utc(...).tz(name)` inside the `louislam/uptime-kuma:1.23.17` image (Node 18.20.3, ICU 74.2), which refused only `Europe/Zaporizhzhia`; 2.x: the `@vvo/tzdb` names measured the same way inside `louislam/uptime-kuma:2.5.11` (Node 22.23.5, ICU 78.3), which refused none of the 315. A fixed list rather than the CLI's own `Intl` set, because Kuma stores the whole settings object before `checkTimezone` refuses, and names the CLI runtime's ICU knows (`America/Coyhaique`) can still be refused by Kuma's; the CLI refuses lowercase names and offset forms like `+09:00` (Kuma stores `+09:00` and then answers "Invalid timezone"), and also names neither UI offers even where Kuma would take them (`Japan`, `Etc/GMT±N`) — narrower than earlier revisions of this PR, which followed the CLI's own ICU; `entryPage` `dashboard` or `statusPage-<slug>`; `primaryBaseURL` an http(s) URL or empty containing no `?` or `#` at all (a bare trailing one included) — they would break the `/api/push/<token>` URL that push monitors build on it — and given through `--config-file` when it carries userinfo, since `--set` puts it in argv; `keepDataPeriodDays` an integer of 0 or more; `tlsExpiryNotifyDays` and `domainExpiryNotifyDays` arrays of positive integers (sent sorted and de-duplicated, like the UI keeps the lists); `chromeExecutable`, `steamAPIKey` and `globalpingApiToken` strings
- `entryPage=statusPage-<slug>` is checked against the pushed `statusPageList` after connecting — an unknown slug exits 1 before `setSettings` is sent, and only then does the command wait for that list
- `steamAPIKey` and `globalpingApiToken` are refused in `--set` — exit 2 pointing at `--config-file` — so the secrets stay out of argv; `--config-file` accepts them and they print as `"***"` in the result, and the literal `"***"` is refused there too
- precedence: fetched < `--config-file` < `--set`
- Kuma 1.23.17's `setSettings` has no version check, so a key another client changes between this command's `getSettings` and its `setSettings` is overwritten with the fetched value (the web UI behaves the same); do not run settings changes against the same instance concurrently
- like the UI's `saveSettings`, the CLI sends the whole object: it fetches `getSettings`, fills the defaults `loadSettings` applies only where the fetched object lacks them — on 1.x `checkUpdate` true, `searchEngineIndex` / `dnsCache` / `trustProxy` false, `entryPage` "dashboard", `nscd` true, `keepDataPeriodDays` 180, `tlsExpiryNotifyDays` `[7, 14, 21]`; on 2.x the same minus `dnsCache` plus `domainExpiryNotifyDays` `[7, 14, 21]` — merges the overrides and sends `setSettings (merged, password)`. The whole object is required, not cosmetic: the handler reads `disableAuth`, `entryPage`, `chromeExecutable`, `nscd` and `serverTimezone` unconditionally, so a partial object would reset `entryPage`, restart Chrome, toggle nscd and — with auth currently disabled — disconnect every other client
- `currentPassword` is the CLI's login password — the same credential `login` used, never an argument and never printed. The server checks it only when the request turns `disableAuth` on while auth is currently enabled; a wrong one answers `ok:false "Incorrect current password"` and exits 1. Turning `disableAuth` back off disconnects every other client of the user (GHSA-23q2-5gf8-gjpp); the requesting socket is excluded, so the command survives and prints the re-read settings
- `chromeExecutable` and `nscd` changes take effect immediately (Chrome reset / nscd services started or stopped); `serverTimezone` is applied globally on every save
- after `setSettings` answers ok the CLI re-reads `getSettings` for the printed result; if that read fails with a CLI error other than exit 70 (an unexpected shape stays exit 70) it prints the sent merged object redacted plus a one-line stderr warning and exits 0 — the save already happened, same degraded contract as `status-pages save`
- a `setSettings` timeout exits 2, but the write may already have been applied and other clients may already have been disconnected by an auth transition — re-run `settings get` to see the stored state before retrying
- Kuma's `ok:false` exits 1 with its `msg`

### api-keys

- API keys come from the pushed `apiKeyList` (`APIKey.toPublicJSON` rows `{ id, name, userID, createdDate, active, expires, status }`); the stored secret `key` is never sent and `status` is Kuma's computed `active` / `inactive` / `expired`. `userID` and `createdDate` are pushed but not printed
- `api-keys list`: `[{ id, name, expires, active, status }]` sorted by id; `active` prints as a boolean although Kuma sends the BOOLEAN column's 0/1; `expires` is the stored local datetime string or null
- `api-keys add --name <name> [--expires <datetime>]`: sends `addAPIKey` with `{ name, expires, active: 1 }` — the APIKeyDialog.vue save payload (`active` is always 1 on add; Kuma has no edit event). `--expires` takes the same offset-free local ISO 8601 datetime as the maintenance flags minus fractional seconds (the datepicker's `modelType` has none, and a DATETIME column cannot keep them on every supported DB) and is sent in its `yyyy-MM-dd HH:mm:ss` spelling — a space-separated local datetime stored verbatim and read as server-local time by `getStatus`; a date before the CLI host's today exits 2 like the UI's `minDate`, and omitting the flag sends `expires: null` ("Don't expire"). Prints `{ id, name, expires, active, key }` where `key` is the one-time clear key — it cannot be read again, so `add` warns on stderr
- `addAPIKey` also sets `apiKeysEnabled` unconditionally and nothing ever sets it back — not delete, not the UI — so the first key switches `/metrics` from user basic auth to API-key-only auth (the key goes in the basic-auth credential slot) and stays that way even after every key is deleted, when `/metrics` then rejects every request. `add` warns on stderr about the switch; a Prometheus or other scraper still using login credentials breaks at that moment
- a timed-out or `ok:false` `addAPIKey` can still leave the row saved — the handler saves before it answers — so after such a failure check `api-keys list` and `delete` the orphan; its clear key is lost either way
- `api-keys enable <id>` / `api-keys disable <id>`: the id is checked against the pushed list first (exit 1) because the UPDATE answers ok even when nothing matches — and does not scope by user, so the check is also what keeps the CLI from flipping another user's key. Prints `{ id, active }`
- `api-keys delete <id> --yes`: without `--yes` exits 2 before connecting; the id is checked against the pushed list first (exit 1) because the user-scoped DELETE still answers ok for an unknown id. Prints `{ id, deleted: true }`
- the id pre-check and the mutation are not atomic for enable / disable / delete: a key another client deletes between the pushed `apiKeyList` read and the request still gets Kuma's ok — the printed success only reflects the list as the command saw it

### housekeeping

- `clear-statistics --yes`: sends `clearStatistics` — `DELETE FROM heartbeat`, so every monitor loses its beats, events and the uptime / ping stats derived from them (on 2.x the stat tables are cleared as well and active monitors restart) — and prints `{ cleared: "statistics" }`; without `--yes` exits 2 before connecting

### database

- `database size`: sends `getDatabaseSize` and prints `{ sizeBytes }`, the database file's size in bytes
- `database shrink --yes`: sends `shrinkDatabase` (SQLite `VACUUM`) and prints `{ shrunk: true }` on 2.x and `{ started: true }` on 1.x; without `--yes` exits 2 before connecting. On 2.x Kuma answers only after VACUUM finishes, which on a large database can outlast `UPTIME_KUMA_TIMEOUT`, so this one request waits up to `UPTIME_KUMA_SHRINK_TIMEOUT` (default 600s) instead. On a 2.x non-sqlite backend both database commands exit 2

## Tests

- `bun test` runs the unit tests in `tests/` against `tests/helpers/fake-kuma.ts`, an in-process Socket.IO server that mimics Kuma 1.23.17; `tests/helpers/run.ts` invokes the CLI in-process (`runCli`) so `bun test --coverage` instruments `src/commands` too — a spawned child process would leave them unmeasured
- `tests/cli-process.test.ts` is the exception: it spawns `bun src/cli.ts` for real to prove the entry point boots, propagates its exit code, and that `disconnect()` lets the process exit instead of hanging on the socket
- `tests/src-files.test.ts` imports every module under `src/` so a file no test loads still appears in the coverage report at 0% instead of being absent
- `bun run test:integration` (`scripts/integration.ts`) runs `tests/integration/` — the same CLI — against a real `louislam/uptime-kuma:1.23.17` container from `tests/integration/compose.yaml` (or the image in `UPTIME_KUMA_IT_IMAGE`; CI also runs 2.5.11, where tests marked `skipIf(on2x)` with their issue number are skipped); it needs Docker. It builds the host binary with `scripts/build.ts` first and exports it as `UPTIME_KUMA_IT_BIN`, which — while `UPTIME_KUMA_IT_URL` marks the integration environment — makes `tests/helpers/run.ts` spawn that binary instead of calling `runCli`, so the suite exercises the compiled artifact, not only the in-process entry point

## Coverage gates (CI)

- The `coverage` job runs `bun test --coverage --coverage-reporter=lcov --coverage-dir=coverage` then `bun scripts/coverage.ts whole` — src/ line coverage must be >= 90%; the script refuses to pass when a src file is missing from the lcov report
- On pull requests it also runs `bun scripts/coverage.ts diff --base <base sha>`: added/changed src/ lines from `git diff <base>...HEAD` are intersected with the lcov `DA` records and must be >= 90% covered; a diff with no measurable src/ lines (docs, config, tests only) passes
- Locally: `bun test --coverage --coverage-reporter=lcov --coverage-dir=coverage` then `bun scripts/coverage.ts whole` / `bun scripts/coverage.ts diff --base origin/main`

## Mutation report (CI, report-only)

- The `mutation` job runs `bun scripts/mutation-report.ts --base <base sha>` on pull requests: for each changed src/ file it generates mewt mutants, keeps high/medium severity mutants whose line range intersects the PR's added lines, and runs the file's focused unit tests (`MUTATION_TESTS` in the script — `tests/mutation-report.test.ts` fails when a new src file lacks an entry). mewt 4.0.0 is installed inside the job only — it publishes no builds for linux-arm64 or macOS-x64, so it cannot live in `.mise.toml` where `mise install` would fail on those platforms
- Surviving mutants (`Uncaught`) are upserted as a PR comment marked `<!-- mutation-testing -->`; the job is `continue-on-error` and never blocks merge — surviving mutants are a report, not a gate. A run that fails before producing a report still upserts a comment saying so (with the run URL), so a stale result never passes for the latest one
- Locally: `mise use -g github:trailofbits/mewt@4.0.0` once (needs linux-x64 or macOS-arm64), then `mise exec -- mewt print mutants --target src/commands/tags.ts` to inspect mutants, or `bun scripts/mutation-report.ts --base origin/main` for the same report CI posts; the script prints the full survivor list to stdout because the PR comment caps its list at GitHub's comment size limit

## Operational notes

- `bun scripts/coverage.ts diff --base <ref>` measures committed changes only — it diffs the merge-base of `<base>` and `HEAD`, so uncommitted work is invisible, and a line that only moved or was re-wrapped counts as deleted+added even though its code did not change. It reads the lcov report as-is and skips added lines with no `DA` record, so a stale report can pass `n/a` over real changes — or, when line numbers drifted, attribute another line's records and pass a wrong ratio: commit first, re-run `bun test --coverage --coverage-reporter=lcov --coverage-dir=coverage`, then measure.
- Two `bun run test:integration` runs cannot share a port: `scripts/integration.ts` derives the compose project name from it (`uptime-kuma-cli-it-<port>`), so a second run on the default `127.0.0.1:3901` removes the first run's Kuma with the `down -v` it always issues before its own `up` — the bind itself only collides with a process outside the runner. A parallel run on the same checkout only needs `UPTIME_KUMA_IT_PORT` set to a free port: the project name follows it, and the binary already builds in a per-run scratch dir instead of `dist/`. Budget for a leg taking on the order of ten-plus minutes (the 2.x leg alone runs about 15–17 minutes in CI).
- CodeQL findings can be checked without opening the Security tab or downloading SARIF: `gh api --paginate "repos/TakashiAihara/uptime-kuma-cli/code-scanning/analyses?ref=<ref>"` lists analyses newest-first and `results_count` is each one's finding count (quote the endpoint — zsh expands a bare `?` as a glob). PR heads work too (`ref=refs/pull/<N>/head`) — a commit gets one analysis per language category (`/language:actions`, `/language:javascript-typescript`), so match `commit_sha` rather than reading only the newest entry, and note a pull-request analysis counts only findings in the change; for the whole tree's open alerts use `gh api --paginate "repos/TakashiAihara/uptime-kuma-cli/code-scanning/alerts?ref=<branch>&state=open"`.
