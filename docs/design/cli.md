# uptime-kuma-cli design

## Goal

- Operate an Uptime Kuma 1.23 instance from the shell and from agents without writing ad hoc `uptime-kuma-api` scripts
- Cover what existing CLIs lack: proxies, notification tests, and status changes (important heartbeats)

## Why not an existing CLI

- BigBoot/AutoKuma `kuma` (Rust): monitors and notifications via JSON files; no beats, no status changes, no proxies, no notification test; targets Kuma v2 by default since 2.0.0
- pablofmorales/kuma-cli (TypeScript): monitors and beats, but no proxies, no notification edit/test, no keyword / json-query fields, and it stores the login token in its config file

## Transport

- Socket.IO v4 client (`socket.io-client`) against the Kuma base URL, `transports: ["websocket"]`
- Kuma 1.23 has no OpenAPI / REST API for management (only badge, push, status page and metrics are REST), so the CLI talks Socket.IO
- Log in with `login` `{ username, password, token: "" }`; the callback returns `{ ok, msg }`
- After login the server pushes `monitorList` (object keyed by id), `maintenanceList` (object keyed by id), `notificationList` (array), `proxyList` (array), `dockerHostList` (array), then `statusPageList` (object keyed by id) about 500ms later, then one `heartbeatList (monitorID, beats)` and one `importantHeartbeatList (monitorID, beats)` per monitor. There is no pushed tag list: each monitor's `tags` is the `monitor_tag`⋈`tag` join (`{ id, monitor_id, tag_id, value, name, color }`, ordered by tag name) and the tag table itself is only readable through `getTags`
- The CLI waits after login only for the lists the command reads: `monitorList`, `notificationList`, `proxyList` and `dockerHostList` for every command, `maintenanceList` for the maintenance commands, `statusPageList` for `maintenance status-pages`, every `status-pages` command and `settings set` when its `entryPage` override names a status page — waiting for the delayed `statusPageList` unconditionally would add its ~500ms to every command
- Request events used, all with a trailing callback returning `{ ok, msg, ... }`:
    - `add (monitor)` → `monitorID`
    - `editMonitor (monitor)` → `monitorID`
    - `getMonitor (id)` → `monitor`
    - `pauseMonitor (id)` / `resumeMonitor (id)`
    - `getMonitorBeats (id, hours)` → `data` (oldest first, raw heartbeat rows with `important`)
    - `addNotification (notification, idOrNull)` → `id`; the server stores the whole object as the `config` JSON string
    - `testNotification (notification)` → `msg`
    - `addProxy (proxy, idOrNull)` → `id`
    - `deleteMonitor (id)` / `deleteNotification (id)` / `deleteProxy (id)`
    - `getTags ()` → `tags` (`{ id, name, color }` rows)
    - `addTag ({ name, color })` → `tag`; `editTag ({ id, name, color })` → `tag` (overwrites both fields, `ok:false "Tag not found"` for an unknown id); `deleteTag (id)` answers ok even for an unknown id
    - `addMonitorTag (tagID, monitorID, value)` / `editMonitorTag (tagID, monitorID, value)` / `deleteMonitorTag (tagID, monitorID, value)`; none of them pushes `monitorList` again, so the CLI's pushed copy goes stale within a run (each command logs in once, so the next run sees the new state)
    - `addMaintenance (maintenance)` → `maintenanceID`; `editMaintenance (maintenance)` runs `jsonToBean`, which overwrites every field it reads, so an edit sends the whole fetched object; `getMaintenance (id)` → `maintenance`; `deleteMaintenance (id)` / `pauseMaintenance (id)` / `resumeMaintenance (id)` answer `{ ok, msg }`
    - `getMonitorMaintenance (id)` → `monitors` (`{ id }` rows); `addMonitorMaintenance (id, [{ id }])` DELETEs the maintenance's `monitor_maintenance` rows and INSERTs the sent ids — it replaces the whole set, it does not add
    - `getMaintenanceStatusPage (id)` → `statusPages` (`{ id, title }` rows); `addMaintenanceStatusPage (id, [{ id }])` replaces the `maintenance_status_page` set the same way
    - `getStatusPage (slug)` → `config` (`StatusPage.toJSON`); `addStatusPage (title, slug)` → `{ ok, msg }` only; `saveStatusPage (slug, config, imgDataUrl, publicGroupList)` → `{ ok, publicGroupList }` (the sent groups mutated with their ids); `deleteStatusPage (slug)` → `{ ok }`; `postIncident (slug, { title, content, style })` → `incident` (`Incident.toPublicJSON`); `unpinIncident (slug)` → `{ ok }`. None of them re-pushes `statusPageList` — `sendStatusPageList` only runs in `afterLogin`
    - `getSettings ()` → `data` (the general settings object, `serverTimezone` filled from the server when unset); `setSettings (data, currentPassword)` → `{ ok, msg }` — `Settings.setSettings` upserts only the keys present in `data`, but the handler also reads `disableAuth`, `entryPage`, `chromeExecutable`, `nscd` and `serverTimezone` unconditionally, so a partial object would reset `entryPage`, restart Chrome, toggle nscd and could disconnect every other client
- A request whose callback has `ok: false` exits 1 with `msg` on stderr

## Configuration

- `$XDG_CONFIG_HOME/uptime-kuma-cli/config.toml` (or `~/.config/uptime-kuma-cli/config.toml`)
    - `url`, `username_command`, `password_command`
- `*_command` runs with `sh -c`; the first stdout line, minus a trailing `\r`, is the secret (spaces are kept). An env value takes precedence and the command does not run
- Accounts with 2FA are not supported: Kuma answers `tokenRequired` and the CLI exits 2
- Each command logs in once. Kuma limits logins to 20 per minute for the whole instance, so a loop of many commands can lock out the UI login for a while
- With an `http://` URL the login travels in clear text; use `https://` when the path leaves a trusted network
- Env: `UPTIME_KUMA_URL`, `UPTIME_KUMA_USERNAME`, `UPTIME_KUMA_PASSWORD`, `UPTIME_KUMA_TIMEOUT` (seconds, default 30, for connect + login + each request), `UPTIME_KUMA_COMMAND_TIMEOUT` (seconds, default 60)
- The username command does not see the password and vice versa

## Output

- stdout is JSON (pretty, 2-space indent), stderr is for messages
- `notificationIDList` is always printed as a sorted array of numbers, whether Kuma sent `{ "3": true }` or `[3]`
- Monitor `tags` print as `[{ tagId, name, value }]`, normalized from the `monitor_tag`⋈`tag` join rows Kuma sends
- Notification configs and proxy passwords are never printed
- Monitor fields that hold secrets (`basic_auth_pass`, `oauth_client_secret`, `tlsKey`, `headers`, `body`, `grpcBody`, `grpcMetadata`, `mqttPassword`, `radiusPassword`, `radiusSecret`, `databaseConnectionString`, and every `kafkaProducerSaslOptions` value other than `mechanism` / `username` / `awsRegion` / `accessKeyId`) print as `"***"` when non-empty; `pushToken` stays visible because pushers need it
- A password inside a monitor `url` (`https://user:pass@host/`) prints as `***` in `monitors list` / `get` / `edit` and in the `publicGroupList` monitors of `status-pages get` / `save` (Kuma adds the url there when `sendUrl` is on)
- `steamAPIKey` in `settings get` / `settings set` output prints as `"***"` when non-empty — it is the only secret among the general settings; a password inside `primaryBaseURL` redacts the same way as a monitor url

## Exit codes

| code | meaning |
|---|---|
| 0 | done |
| 1 | Kuma answered no (`ok: false`, unknown id) |
| 2 | configuration, usage (including a missing subcommand), connection, login, disconnect, or timeout failure |
| 3 | a create or attach was skipped because it already exists (`monitors add` / `tags add` / `maintenance add` same name or title, `status-pages add` same slug, `status-pages save` slug rename onto another page, `monitors tag` same tag+value) |
| 70 | unexpected error |

## Commands

### monitors

- `monitors list [--name <substring>] [--tag <name>]`
    - array sorted by id of `{ id, name, type, active, url, hostname, port, interval, parent, notificationIDList, tags }`; `tags` is `[{ tagId, name, value }]` from the monitor's `monitor_tag`⋈`tag` join
    - `--name` filters case-insensitively; `--tag` keeps monitors that have a tag whose name equals the argument exactly (case-sensitive); the two combine
- `monitors get <id>`: the monitor object from `monitorList` with `notificationIDList` as an array and `tags` as `[{ tagId, name, value }]`; unknown id exits 1
- `monitors add --type <group|http|port|ping|keyword|json-query|grpc-keyword|dns|docker|real-browser|push|steam|gamedig|mqtt|kafka-producer|sqlserver|postgres|mysql|mongodb|radius|redis|tailscale-ping> --name <name> [options]` (picker order of EditMonitor.vue)
    - options: `--url`, `--hostname`, `--port`, `--keyword`, `--invert-keyword`, `--json-path`, `--expected-value`, `--packet-size`, `--dns-resolve-server`, `--dns-resolve-type`, `--docker-container`, `--docker-host`, `--game`, `--grpc-url`, `--grpc-service-name`, `--grpc-method`, `--grpc-protobuf <file>`, `--grpc-enable-tls`, `--mqtt-topic`, `--mqtt-username`, `--mqtt-success-message`, `--kafka-producer-broker <host:port>` (repeatable), `--kafka-producer-topic`, `--kafka-producer-message`, `--kafka-producer-ssl`, `--kafka-producer-allow-auto-topic-creation`, `--radius-username`, `--radius-called-station-id`, `--radius-calling-station-id`, `--database-query <sql>`, `--interval <s>` (60), `--retry-interval <s>`, `--max-retries <n>` (0), `--resend-interval <n>` (0), `--timeout <s>` (positive; the timing rule is below), `--proxy-id <id>`, `--notification-id <id>` (repeatable), `--notifications-from <monitorId>`, `--parent <groupId>`, `--paused`, `--push-token <token>`, `--tag <tagId[:value]>` (repeatable), `--set <key>=<value>` (repeatable), `--config-file <json>`
    - required per type: http / keyword / json-query / real-browser need `--url`; keyword and grpc-keyword need `--keyword`; json-query needs `--json-path` and `--expected-value`; grpc-keyword also needs `--grpc-url`, `--grpc-service-name`, `--grpc-method` and `--grpc-protobuf` (Kuma 1.23.17 always runs `protojs.parse` on the proto and `JSON.parse` on `grpcBody` at check time, so the proto cannot be empty); port / steam / gamedig need `--hostname` and `--port`; ping / dns / tailscale-ping / radius need `--hostname`; mqtt needs `--hostname`, `--port` and `--mqtt-topic`; kafka-producer needs `--kafka-producer-broker` (each a `host:port` string), `--kafka-producer-topic` and `--kafka-producer-message`; radius also needs `--radius-username`, `--radius-called-station-id` and `--radius-calling-station-id` — its secrets `radiusPassword` / `radiusSecret` can only come from `--config-file` and are checked on the merged monitor; docker needs `--docker-container` and `--docker-host <docker host id>`; gamedig also needs `--game`; sqlserver / postgres / mysql / mongodb / redis need `databaseConnectionString` — a secret that only `--config-file` can supply (`--set` refuses it), so a missing or empty one exits 2 on the merged monitor after connecting, with a message naming the field; mysql's optional password is `radiusPassword`, also `--config-file` only. Missing flag values exit 2 before connecting
    - type-specific defaults: ping `--packet-size` (56); dns `--port` (53) and radius `--port` (1812), both from the UI's type watcher; gamedig sends `gamedigGivenPortOnly: true`; `--grpc-protobuf` reads the proto file and sends its content like the UI textarea; grpc-keyword sends `grpcBody: "{}"` unless `--config-file` overrides it (Kuma 1.23.17 JSON.parses it at check time and protobufjs rejects a null request); `--invert-keyword` applies to keyword and grpc-keyword; `--database-query` is sent only for sqlserver / postgres / mysql — on the other types it is ignored like every type-specific flag. The database types get no `databaseConnectionString` default: the UI's type watcher would prefill a template such as `postgres://username:password@host:port/database`, the CLI sends nothing. The CLI does not check an mqtt `mqttTopic`; Kuma 1.23.17 compares the received topic with `===`, so a wildcard like `sensors/#` never matches and the monitor times out
    - `--set` / `--config-file` are the escape hatch for fields without a dedicated flag: the value parses as JSON when it parses, else stays a string. Every key must be a monitor field the `add` event accepts (the `MONITOR_ADD_FIELDS` set in `src/kuma.ts`; the test fake keeps its own copy of the accepted columns); `id`, `type` and `name` are refused (use `--type` / `--name`), and an unknown key exits 2 naming it before connecting. Precedence: UI defaults < typed flags < `--config-file` < `--set`
    - a hatch key that has a typed flag goes through the flag's validation (`interval`, `retryInterval`, `resendInterval`, `maxretries`, `timeout`, `port`, `packetSize`, `dns_resolve_type`, `proxyId`, `parent`, `docker_host`), and `accepted_statuscodes` must be an array of strings, `kafkaProducerBrokers` an array of `host:port` strings — the `host:port` rule is the CLI's, the 1.23.17 UI does not check it, but kafkajs splits each broker on `:` so a host containing `:` cannot work — and `kafkaProducerSaslOptions` an object whose `mechanism` is one of the UI's values (`None`, `plain`, `scram-sha-256`, `scram-sha-512`, `aws`); invalid exits 2 naming the key before connecting, and valid values are coerced to the flag's type
    - secret fields (`basic_auth_pass`, `oauth_client_secret`, `tlsKey`, `headers`, `body`, `grpcBody`, `grpcMetadata`, `mqttPassword`, `radiusPassword`, `radiusSecret`, `databaseConnectionString`, `kafkaProducerSaslOptions`) are refused in `--set` — exit 2 pointing at `--config-file` — so they stay out of argv; `--config-file` accepts them
    - like the UI, notifications marked default are always attached, and every type except port / push gets the default proxy unless `--proxy-id` is given (the UI assigns it on add for all types; only the proxy picker is limited to http / keyword / json-query)
    - `--parent <groupId>` must be an existing monitor of type `group` in the pushed `monitorList`; an unknown id or a non-group exits 1. The parent value is normalized before sending — a numeric string becomes a number, an empty string exits 2, `null` clears — and the group check runs on the final merged value whichever source set it. `--parent` cannot be combined with a `parent` key in `--set` / `--config-file` — that exits 2 (`use either --parent or a parent key, not both`); between the two hatch sources `--set` still wins
    - `--docker-host` and a hatch `docker_host` must name an id in the pushed `dockerHostList`; an unknown id exits 1 (`docker host <id> not found`) before `add` is sent. For `--type docker` a hatch `docker_host: null` overrides the flag's host, so the monitor would have none — exit 2 naming the hatch source (`--set docker_host must be a docker host id`)
    - same name (exact match) already present: print `{ id, name, skipped: true }` and exit 3 without sending `add`
    - the payload starts from the Kuma 1.23 UI defaults (`accepted_statuscodes: ["200-299"]`, `method: "GET"`, `maxredirects: 10`, `kafkaProducerBrokers: []`, `kafkaProducerSaslOptions: { mechanism: "None" }`, ...) and sends `notificationIDList` as `{ "<id>": true }`
    - `--notifications-from` copies that monitor's notifications; `--notification-id` adds to them (both on top of the defaults)
    - timing: `interval` must be 20–2073600 seconds — the bounds Kuma 1.23.17 `Monitor.validate()` enforces before storing, so the CLI checks a user-supplied value (flag or hatch) against them up front. `retryInterval` defaults to the interval and `timeout` defaults to 48, both computed from the final interval after `--config-file` / `--set`. An explicit `retryInterval` or `timeout` from any source is kept, except that `timeout` never exceeds 80% of the final interval — a larger explicit value is capped to it (the same rule the flags always had). `timeout` must be positive: Kuma 1.23.17 `monitor.js` replaces a timeout of 0 (or less) with `interval * 1000 * 0.8` at check time and then multiplies by 1000 for axios, so 0 would silently become a timeout of interval × 800 seconds — the CLI refuses it with exit 2
    - push: `pushToken` precedence is generated default < `--push-token` < `--config-file` < `--set`; a random 32-char token is generated only when none of the three is given. The merged value must be a non-empty string — anything else exits 2 — and it is what gets sent and printed
    - `--paused` sends `active: false`, so Kuma does not start the monitor
    - `--tag <tagId[:value]>` attaches tags after `add` succeeds: each id must exist in `getTags` (exit 1 before `add` is sent), the value defaults to `""` and may contain colons, and the same `tagId:value` twice exits 2 before connecting. `addMonitorTag` is sent per tag; if one answers `ok:false` after the monitor was created the command exits 1 — stdout prints the monitor with the tags attached so far and stderr names the failing tag and that the monitor exists. A timeout or disconnect exits 2 like every other timeout, and an attach that timed out may still have happened server-side
    - prints `{ id, name, type, active }`, `tags` (`[{ tagId, name, value }]`, only when `--tag` was given), plus `pushToken` and `pushUrl` (`<base>/api/push/<token>?status=up&msg=OK&ping=`, where base is the Primary Base URL setting when set, else the CLI url) for push
- `monitors edit <id> [--set <key>=<value>...] [--config-file <json>] [--parent <groupId|none>]`
    - fetches the monitor with `getMonitor`, merges `--config-file`, then `--set` over it, applies `--parent`, and sends `editMonitor`; at least one of the three is required. `--parent` cannot be combined with a `parent` key in `--set` / `--config-file` — that exits 2 (`use either --parent or a parent key, not both`); between the two hatch sources `--set` still wins
    - same field and value validation as add: every key must be a monitor field, `id` exits 2, hatch values for typed-flag keys go through the flag's validation (`type` included — it must be one of the picker types), and secret fields are refused in `--set` and accepted in `--config-file`. Unlike add, `name` and `type` may be set here
    - `notificationIDList` accepts an array or an object of positive integer ids and is sent as an object (Kuma 1.23 iterates it with `for...in`, so an array would be stored as its indexes)
    - the parent checks run on the final merged value whichever source set it: a `parent` from `--set`, `--config-file` or `--parent` naming the monitor itself exits 2 — Kuma 1.23 rejects only descendants, and a self-parent makes its parent walk loop forever
    - a parent value is normalized before sending (a numeric string becomes a number, an empty string exits 2, `null` clears), and the final value must be an existing monitor of type `group` in the pushed `monitorList` — exit 1 otherwise, including a `--set parent`; `--parent none` sends `parent: null` to clear it
    - `docker_host` and `proxyId` are checked against the pushed `dockerHostList` / `proxyList` when the edit sets them (see the shared validation note below)
    - for a push monitor a `pushToken` the edit sets must be a non-empty string — anything else exits 2 before `editMonitor` is sent
    - `retryInterval` / `timeout` derive from the interval only when the edit touches `interval` or `timeout`; a stored `timeout: 0` is otherwise sent back untouched even though Kuma 1.23.17 runs it as interval × 800 seconds on HTTP checks. The UI may legitimately store `timeout: 0`, a deleted docker host as `docker_host: null`, `proxyId: 0` or `port: 0`
    - a `type` change keeps the stored fields the new type shares: editing a `radius` monitor to `mysql` keeps the stored `radiusPassword`, which Kuma 1.23.17 reads as the MySQL password — the UI stores both in that one field
    - prints the monitor as Kuma saved it (fetched again with `getMonitor`), redacted and with `tags` normalized as in `monitors get`; Kuma ignores some fields here (`active`), and this shows it
- `add` and `edit` both run `validateFinalMonitor` on the merged monitor right before sending, but with different scope. On `add` the whole monitor is judged: the per-type required fields must be present (`url`, `keyword`, `jsonPath` + `expectedValue`, `grpcUrl` + `grpcServiceName` + `grpcMethod` + `grpcProtobuf` for grpc-keyword, `hostname`, `port`, `mqttTopic`, `kafkaProducerTopic` + `kafkaProducerMessage` + a non-empty `kafkaProducerBrokers`, the five `radius*` fields including the secret `radiusPassword` / `radiusSecret`, `game`, `docker_container` + `docker_host`, `pushToken`, `databaseConnectionString` for sqlserver / postgres / mysql / mongodb / redis, and `dns_resolve_server` for `dns`), `parent` must be null or an existing group, and `docker_host` / `proxyId` must name ids in the pushed `dockerHostList` / `proxyList`. On `edit` only the fields the edit sets are judged the same way, plus every required field of the new type when `type` changes — a stored value the edit does not touch is never re-judged. A hatch `type` on edit must be one of the 22 types the 1.23.17 picker offers; anything else exits 2
- `monitors pause <id>` / `monitors resume <id>`: prints `{ id, active }`
- `monitors delete <id> --yes`: sends `deleteMonitor` and prints `{ id, deleted: true }`; without `--yes` exits 2 before connecting. The id is checked against the pushed `monitorList` first because Kuma 1.23 answers ok even for an unknown id. The monitor's `monitor_tag` rows are deleted with it (foreign key cascade). Deleting a group monitor does not delete its children: their `parent` becomes null (Kuma 1.23 `ON DELETE SET NULL`), so they become top-level monitors and keep their own active / paused state, and the monitor's heartbeats are deleted with it
- `monitors tag <id> --tag <tagId> [--value <value>]`: attaches the tag; `--value` defaults to `""` (never sent as null). The monitor must be in the pushed `monitorList` and the tag in `getTags` — exit 1 each. `addMonitorTag` has no unique constraint, but the same tag+value already attached prints `{ id, tagId, value, skipped: true }` and exits 3 without sending. Otherwise sends `addMonitorTag` and prints `{ id, tagId, value }`
- `monitors untag <id> --tag <tagId> [--value <value>]`: `--value` defaults to `""`; the monitor must have that exact tag+value in the pushed list, else exit 1 — `deleteMonitorTag` answers ok even when nothing matches. A stored null value can never match `value = ?`, so removing one exits 1 with a message saying Kuma cannot remove a tag whose value is null through this event. Prints `{ id, tagId, value, removed: true }`
- `monitors retag <id> --tag <tagId> --value <value>`: the monitor must have the tag (exit 1); sends `editMonitorTag`, which sets the value on EVERY attachment of that tag on the monitor and answers ok even when nothing matches. A monitor that has the tag attached more than once exits 1 before sending — use `untag` + `tag` instead, since retagging would collapse the rows into identical duplicates. Prints `{ id, tagId, value }`
- none of `addMonitorTag` / `editMonitorTag` / `deleteMonitorTag` pushes `monitorList` again; each command logs in once, so the next run sees the new state

### beats

- `beats <id> [--hours <n>] [--limit <n>] [--important]`
    - `getMonitorBeats (id, hours)`, default 24 hours; newest first; `--limit` keeps the newest n; `--important` keeps rows with `important` truthy
    - each row `{ time, status, msg, ping, important }`; `status` stays numeric (0 down, 1 up, 2 pending, 3 maintenance)
- `beats latest`
    - waits for `heartbeatList` of every monitor in `monitorList` (until the timeout; missing ones exit 2 naming them)
    - array sorted by id of `{ id, name, active, time, status, msg }`; a monitor with no beat has `time: null, status: null, msg: null`

### events

- `events <id> [--hours <n>] [--by-day]`
    - status changes: `getMonitorBeats (id, hours)` rows with `important` truthy, default 168 hours, newest first, `{ time, status, msg }`
    - `--by-day` prints `[{ date, down, up }]` sorted by date, counting status 0 and 1 per day; Kuma stores `time` in UTC and the day is taken in UTC

### notifications

- `notifications list`: `[{ id, name, type, active, isDefault }]`, `type` read from the `config` JSON
- `notifications add --name <name> --type <type> [--set k=v]... [--config-file <json>] [--default] [--apply-existing]`
    - the notification object is `{ isDefault: false, applyExisting: false, ...config-file, ...sets, name, type }`, then `--default` / `--apply-existing` set their field to true when given; secrets go through `--config-file` so they stay out of argv
    - prints `{ id, name, type }`
- `notifications edit <id> [--set k=v]... [--config-file <json>]`: merges into the stored config and sends `addNotification (merged, id)` with `applyExisting: false` (a stored `true` would re-attach the notification to every monitor on each edit, so `--set applyExisting=...` exits 2); at least one of `--set` / `--config-file`; prints `{ id, name, type }`
- `notifications test <id>`: sends the stored config to `testNotification`; prints `{ id, ok: true, msg }`, Kuma's failure exits 1
- `notifications delete <id> --yes`: sends `deleteNotification` and prints `{ id, deleted: true }`; without `--yes` exits 2 before connecting

### proxies

- `proxies list`: `[{ id, protocol, host, port, auth, username, active, default }]`; `auth` / `active` / `default` print as booleans although Kuma 1.23 sends them as 0/1
- `proxies add --protocol <http|https|socks|socks5|socks5h|socks4> --host <h> --port <p> [--username <u> --password-file <f>] [--default] [--apply-existing]`: prints `{ id }`
- `proxies edit <id> [--set k=v]... [--password-file <f>]`: merges into the listed proxy (password kept as stored unless `--password-file` is given, which also turns `auth` on) and sends `addProxy (merged, id)`; prints `{ id }`
- `proxies delete <id> --yes`: sends `deleteProxy` and prints `{ id, deleted: true }`; without `--yes` exits 2 before connecting. Kuma sets `proxy_id` to null on the monitors that used the proxy, so they stop using any proxy

### tags

- tags are not pushed after login; every tags command asks `getTags` (`{ id, name, color }` rows)
- `tags list`: `[{ id, name, color }]` sorted by id
- `tags add --name <name> --color <#rgb|#rrggbb>`: `--color` must be `#rgb` or `#rrggbb` and `--name` must not be empty (exit 2 before connecting). A tag with the same name (exact) already present prints `{ id, name, skipped: true }` and exits 3 without sending `addTag` — the name is not unique in Kuma, the skip is a CLI convention like `monitors add`. Otherwise sends `addTag` and prints `{ id, name, color }`; an `addTag` answer without `tag.id` exits 70
- `tags edit <id> [--name n] [--color c]`: at least one flag (exit 2 before connecting); `--name` must not be empty, and a `--name` that differs from the current name and is already used by another tag exits 1 naming that tag's id (the 1.23.17 TagEditDialog refuses it too; keeping the current name is fine even when another tag shares it — Kuma allows duplicate names). `editTag` overwrites both fields, so the flag not given keeps the stored value. Unknown id exits 1. Prints `{ id, name, color }`
- `tags delete <id> --yes`: sends `deleteTag` and prints `{ id, deleted: true }`; without `--yes` exits 2 before connecting. The id is checked against `getTags` first because Kuma answers ok even for an unknown id; the monitor_tag rows cascade

### maintenance

- maintenance windows come from the pushed `maintenanceList`; every command checks the id against it before requesting because `getMaintenance` of an unknown id dies inside `toJSON` rather than answering cleanly
- `maintenance list`: array sorted by id of `{ id, title, strategy, active, status }`; `status` is Kuma's computed value (`inactive`, `scheduled`, `under-maintenance`, `ended`, `unknown`)
- `maintenance get <id>`: the `getMaintenance` object; unknown id exits 1
- `maintenance add --title <t> --strategy <s> [--description d] [--start <ISO> --end <ISO>] [--timezone <tz>] [--paused] [--config-file <json>]`
    - `--strategy` is one of `manual`, `single`, `cron`, `recurring-interval`, `recurring-weekday`, `recurring-day-of-month`
    - the payload starts from the UI's `isAdd` defaults (`cron: "30 3 * * *"`, `durationMinutes: 60`, `intervalDay: 1` — the UI caps it at 3650 and so does the CLI — `timeRange` 02:00–03:00, empty `weekdays` / `daysOfMonth`, `dateRange: []`, `active: true`); `dateRange` is always an array because `jsonToBean` indexes `dateRange[0]` unconditionally. One default differs on purpose: the UI sends `timezoneOption: null` where the CLI sends `"SAME_AS_SERVER"` — same effect, the server timezone
    - `--start` / `--end` are the UI's "Effective Date Range" and take local ISO 8601 datetimes without an offset (`Z` and `±hh:mm` exit 2 — Kuma reads the strings as local time in `timezoneOption`, so an offset would be misparsed). The datetime must be a real calendar date — the day must exist in its month (leap years included) and hour/minute/second stay in range, so `2031-02-31` and `T24:00` exit 2 like the UI's datetime-local never producing them. Every strategy except `manual` accepts them, `single` requires both (end after start), and the UI allows a start without an end so `--start` alone sends `[start]` — exit 2 before connecting on a violation. Whether `single` needs the range is judged on the merged strategy and `dateRange`, so a `--config-file` `strategy` or `dateRange` decides it too. `cron` and the `recurring-*` strategies take a start but never an end: Kuma 1.23.17's `Maintenance.run` leaves `duration` undefined when `end_date` is set and the remaining time is >= duration, so `setTimeout(..., undefined)` ends the window immediately — the CLI refuses an end date for them (exit 2)
    - `--timezone` takes an IANA name or `SAME_AS_SERVER`; an invalid name exits 2 because `dayjs.tz` throws inside `toJSON` and would break the `maintenanceList` push for every client
    - `--config-file` is merged after the typed flags and carries the schedule fields of the other strategies: `cron` needs `cron` — a croner 6.0.7 nickname (`@yearly`, `@annually`, `@monthly`, `@weekly`, `@daily`, `@hourly`) or a 5 or 6 whitespace-separated field expression in croner's shape: the first `L` is stripped from day-of-month and day-of-week, month and day-of-week parts of 3+ chars may use the JAN-DEC / SUN-SAT names (converted to numbers), the first `?` of each part becomes a number, and what remains may only contain `[0-9*/,-]`; an empty part (surrounding whitespace) and a bare day-of-week `L` are refused too, because croner parses them but never schedules a run — and `durationMinutes` (positive integer); every `recurring-*` needs `timeRange` (two `{hours, minutes, seconds?}` objects with seconds in 0–59), `weekdays` (integers 0–6), `daysOfMonth` (integers 1–31 or `"lastDay1"`) and `intervalDay` (positive integer up to 3650 — for `recurring-interval` the cap is 31 because `generateCron` emits `*/N` in day-of-month and croner rejects a step over 31); `recurring-weekday` additionally needs a non-empty `weekdays` and `recurring-day-of-month` a non-empty `daysOfMonth`, because `generateCron` joins them into the cron expression. A missing or malformed field exits 2 before connecting instead of failing inside Kuma. The cron check is a shape check: Kuma 1.23.17 calls the async `validateCron` without await, so even a bad expression is stored and the rejection goes unhandled — croner can still refuse values like `L-1` or `13` in the month field. The defaults already satisfy `cron` and `recurring-interval`, so those two need no config file
    - `--config-file` cannot set `id`; same title already present (exact match) prints `{ id, title, skipped: true }` and exits 3 without sending `addMaintenance`
    - prints `{ id, title, strategy, active }`
- `maintenance edit <id> [--title t] [--description d] [--start --end] [--timezone tz] [--set k=v]... [--config-file <json>]`
    - `editMaintenance` runs `jsonToBean` over the whole object, so the CLI fetches the maintenance, merges and sends it back; at least one change is required (exit 2 before connecting)
    - `--start` and `--end` each patch one end of the stored `dateRange` — `--start` replaces index 0, `--end` index 1 — so either may be given alone (`--end` alone needs a stored start, exit 2 otherwise); on add `--end` still requires `--start`, and `manual` takes neither flag on either command. The cron/recurring end-date refusal applies to the merged range too — `edit --end` exits 2, and a strategy change to `cron`/`recurring-*` fails the same way when the stored range has an end (`single` → `cron` included); the error says to drop the end, and for a stored one suggests `--set 'dateRange=["<start>"]'` (quoted for the shell) in local time. Untouched `dateRange` values are not re-judged, so a `--title` edit on a window that already has an end still passes
    - precedence: fetched < `--config-file` < `--set` < typed flags; `id` is refused in `--set` and `--config-file`, and a `strategy` that is not one of the six exits 2 before connecting (the merged-value check still runs after the fetch). The strategy rules (manual takes no range, single needs both, cron/recurring take no end) judge the merged strategy, so a hatch can flip them — e.g. `--set strategy=manual` makes `--start` invalid even on a cron window
    - the same field validation as add runs on the merged object, scoped like `monitors edit`: only touched keys are judged, plus every field the new strategy requires when `strategy` changes — a `--title` edit on a cron maintenance does not re-judge its cron fields. `dateRange` is judged only on the final merged value, so a `--set` can repair a bad `--config-file` range; its entries must be offset-free local ISO datetimes like the flags
    - prints the maintenance as Kuma saved it
- `maintenance pause <id>` / `maintenance resume <id>`: prints `{ id, active }`
- `maintenance delete <id> --yes`: sends `deleteMaintenance`, prints `{ id, deleted: true }`; without `--yes` exits 2 before connecting; unknown id exits 1 because the delete answers ok even for unknown ids
- `maintenance monitors <id>` and `maintenance status-pages <id>` show or change what a maintenance affects: `[{ id, name }]` for monitors, `[{ id, title }]` for status pages, sorted by id
    - `--add <id>` / `--remove <id>` (repeatable) read the current set (`getMonitorMaintenance` / `getMaintenanceStatusPage`), apply the change locally and send the full set; `--set-ids <id,...>` replaces it exactly (`--set-ids ""` clears it) and cannot be combined with `--add` / `--remove` (exit 2). Reading then sending back means a change made in the UI between the read and the write is overwritten — Kuma 1.23 has no compare-and-swap for these sets, so there is no way to prevent it
    - every supplied id must exist in the pushed `monitorList` / `statusPageList` — exit 1 — and the maintenance id is checked against `maintenanceList` first
    - the `add*` events DELETE every row the maintenance has and INSERT the sent ids: they replace the whole set, they do not add. That is why `--add` reads the current set first — sending only the new id would wipe the rest. After a successful write an id that is no longer in the pushed list prints with a `null` name / title instead of failing the command

### status-pages

- status pages come from the pushed `statusPageList` (`StatusPage.toJSON` values keyed by id); every command checks the slug against it before requesting. `unpinIncident` answers ok even for an unknown slug (the UPDATE runs with a NULL page id), while `getStatusPage` / `deleteStatusPage` / `postIncident` answer ok:false — the pre-check gives the CLI's own `status page <slug> not found` either way
- `status-pages list`: the pushed pages as an array sorted by title like Kuma's `ORDER BY title` (the pushed object's numeric keys would enumerate by id, so the title order is restored client-side)
- `status-pages get <slug>`: `getStatusPage`'s `config` merged with `publicGroupList` and the pinned `incident` from `GET <url>/api/status-page/<slug>` — no auth — printed as `{ ...config, publicGroupList, incident }`, `incident` null when none. The route is cached 5 minutes by Kuma (apicache) keyed on the full URL including the query string; `saveStatusPage` and `deleteMonitor` clear it but `deleteStatusPage`, `addStatusPage`, `postIncident` and `unpinIncident` do not — so the CLI adds a unique `?_=<nonce>` query to every read and Kuma's cache never answers it (a reverse proxy that ignores query strings could still serve a stale body). Each such read leaves one entry in Kuma's in-memory apicache for 5 minutes (about 1–2 KB for a small page; `get` adds one, `save` two), the same an anonymous client can already cause on this public route. A network error or timeout on that fetch exits 2 and a non-200 answer exits 1, both naming the URL
- `status-pages add --slug <s> --title <t>`: validates like Kuma before connecting — title trimmed non-empty, slug trimmed, lower-cased and matching `^[a-z0-9]+(?:-[a-z0-9]+)*$` (exit 2). A slug already in `statusPageList` prints `{ id, slug, title, skipped: true }` and exits 3 without sending — `status_page.slug` also has a UNIQUE index. `addStatusPage` answers only `{ ok, msg }` and does not re-push the list, so the new page's `toJSON` is read back with `getStatusPage`
- `status-pages save <slug> --config-file <path>`: the file is a JSON object validated before connecting (exit 2). Allowed keys are `slug`, `title`, `description`, `theme` (`auto` / `light` / `dark`), `showTags`, `footerText`, `customCSS`, `showPoweredBy`, `showCertificateExpiry`, `googleAnalyticsId`, `domainNameList`, `logo`, `publicGroupList`; anything else — `id`, `icon`, `published` included — is refused by name. `slug` is trimmed and lower-cased like the UI's save. Groups keep only `{ id?, name, monitorList: [{ id, sendUrl? }] }` (`sendUrl` also accepts the 0/1 the public JSON emits) and extra keys a `get` output carries — `weight`, `type`, `url`, `tags` — are allowed and ignored, so a `get` result's `publicGroupList` feeds back unchanged
- the save fetches the page like `get` does — the public-route read carries the same cache-busting query, so it never sees a body cached before a delete/re-add — and sends `saveStatusPage` the fetched `toJSON` with the file merged over it — a key the handler reads but the merge lacks would be stored as null — plus the file's `publicGroupList` or, when absent, the fetched groups reduced the same way. `logo` is the `imgDataUrl` argument (a `data:` URL must be `data:image/png;base64,`) and defaults to the fetched `icon`, like the UI; an empty stored icon reads as `/icon.svg` (the UI behaves the same). A `domainNameList` entry is moved off any other page that had it. A file `slug` renaming onto another page's slug prints `{ id, slug, title, skipped: true }` and exits 3; a group `id` that is not a current public group of the page or a monitor `id` missing from `monitorList` exits 1 before saving — an unknown group id would make Kuma's `findOne` return null and throw after the page row was already stored. Groups are replaced wholesale: an entry without `id` is created (Kuma assigns the id), one with an `id` is updated, and every group not listed is deleted. It then prints like `get` under the new slug when it changed; if that read-back fails the save already happened, so the sent config is printed with the save response's `publicGroupList` (it carries the assigned group ids), `incident` null, a one-line warning naming the failure goes to stderr and the exit code stays 0. That degraded stdout is not a fresh read: `incident` null means unknown, the groups are in the reduced save shape, and `icon` is the pre-save one even when the file set `logo`; a script that needs the stored state reads it again with `get`. An unexpected response shape on the read-back (exit 70) is not degraded and still exits 70
- `status-pages delete <slug> --yes`: without `--yes` exits 2 before connecting; unknown slug exits 1 (Kuma's own answer is ok:false "Status Page is not found"). The page's incidents and groups are deleted with it. Prints `{ slug, deleted: true }`
- `status-pages incident <slug> --title <t> --content <c> [--style <s>]`: `--style` is one of `info`, `warning`, `danger`, `primary`, `light`, `dark`, default `primary` (the StatusPage.vue `createIncident` default); title and content must be non-empty (exit 2). `postIncident` unpins every previous incident of the page before pinning the new one. Prints the returned `incident` (`Incident.toPublicJSON`)
- `status-pages unpin <slug>`: prints `{ slug, unpinned: true }`

### settings

- `settings get`: the `getSettings` `data` object as stored; `steamAPIKey` prints as `"***"` when non-empty and a password inside `primaryBaseURL` (`https://user:pass@host/`) prints as `***` like a monitor url
- the `get` output is not a valid `--config-file` as is: it carries keys the UI does not edit (rejected by name) and `steamAPIKey` reads `"***"`, the redacted placeholder — `set` refuses that value with exit 2 and the message says to omit the key to keep the stored value. Copy only the keys being changed
- `settings set [--set <key>=<value>]... [--config-file <json>]`: at least one of the two (exit 2). The allowed keys are the ones the 1.23.17 settings components edit: `serverTimezone`, `searchEngineIndex`, `entryPage`, `primaryBaseURL`, `steamAPIKey`, `nscd`, `dnsCache`, `chromeExecutable`, `checkUpdate`, `checkBeta`, `trustProxy`, `keepDataPeriodDays`, `tlsExpiryNotifyDays`, `disableAuth`; an unknown key exits 2 naming it and its source
- every value is validated before connecting against the UI's type and bounds: the seven booleans must be booleans; `serverTimezone` must be `"UTC"` or a name from `Intl.supportedValuesOf("timeZone")`, compared case-sensitively — the UI's list comes from the `timezones-list` package (`timezoneList()` in util-frontend.js) and the Intl set is the closest available, so aliases like `Japan` and offset forms like `+09:00`, which `Intl.DateTimeFormat` itself accepts, are refused; `entryPage` `dashboard` or `statusPage-<slug>`; `primaryBaseURL` an http(s) URL or empty with no query string or fragment — a `?`/`#` part would break the `/api/push/<token>` URL that push monitors build on it; `keepDataPeriodDays` an integer of 0 or more; `tlsExpiryNotifyDays` an array of positive integers (sent sorted and de-duplicated, like the UI keeps the list); `chromeExecutable` and `steamAPIKey` strings
- `entryPage=statusPage-<slug>` is checked against the pushed `statusPageList` after connecting — an unknown slug exits 1 before `setSettings` is sent, and only then does the command wait for that list
- `steamAPIKey` is refused in `--set` — exit 2 pointing at `--config-file` — so the secret stays out of argv; `--config-file` accepts it and it prints as `"***"` in the result, and the literal `"***"` is refused there too
- precedence: fetched < `--config-file` < `--set`
- like the UI's `saveSettings`, the CLI sends the whole object: it fetches `getSettings`, fills the defaults `loadSettings` applies only where the fetched object lacks them (`checkUpdate` true, `searchEngineIndex` / `dnsCache` / `trustProxy` false, `entryPage` "dashboard", `nscd` true, `keepDataPeriodDays` 180, `tlsExpiryNotifyDays` `[7, 14, 21]`), merges the overrides and sends `setSettings (merged, password)`. The whole object is required, not cosmetic: the handler reads `disableAuth`, `entryPage`, `chromeExecutable`, `nscd` and `serverTimezone` unconditionally, so a partial object would reset `entryPage`, restart Chrome, toggle nscd and — with auth currently disabled — disconnect every other client
- `currentPassword` is the CLI's login password — the same credential `login` used, never an argument and never printed. The server checks it only when the request turns `disableAuth` on while auth is currently enabled; a wrong one answers `ok:false "Incorrect current password"` and exits 1. Turning `disableAuth` back off disconnects every other client of the user (GHSA-23q2-5gf8-gjpp); the requesting socket is excluded, so the command survives and prints the re-read settings
- `chromeExecutable` and `nscd` changes take effect immediately (Chrome reset / nscd services started or stopped); `serverTimezone` is applied globally on every save
- after `setSettings` answers ok the CLI re-reads `getSettings` for the printed result; if that read fails with anything but an exit-70 unexpected shape it prints the sent merged object redacted plus a one-line stderr warning and exits 0 — the save already happened, same degraded contract as `status-pages save`
- a `setSettings` timeout exits 2, but the write may already have been applied and other clients may already have been disconnected by an auth transition — re-run `settings get` to see the stored state before retrying
- Kuma's `ok:false` exits 1 with its `msg`
