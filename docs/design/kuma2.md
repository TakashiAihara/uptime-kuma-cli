# Uptime Kuma 2.x support notes

## Scope

- Compares Uptime Kuma 1.23.17 (the CLI's default target) with 2.5.11 by reading both source trees, for GitHub issue #17
- Only differences that change what the CLI sends, reads, validates or documents are listed; handlers whose only change is formatting or `msgi18n` are folded into one row each
- Citations are `<version>/<path>:<line>` relative to each Kuma clone root; `src/...` paths under a version are Kuma's own UI / shared code, bare `src/...` in the first column are this CLI's files
- Migration file names are cited with a glob (`db/knex_migrations/*-conditions.js`) because the date prefix is not stable text
- Impact values: none (no code change, maybe a doc edit), branch needed (works on 2.x only after a version-specific change), breaks (wrong or failing behaviour on 2.x today), unverified (could not be confirmed from source alone; the row says what would confirm it)
- Nothing here was run against a 2.x server; every claim is from source reading, so rows that depend on runtime behaviour of third-party code (redbean-node, croner, knex) are marked unverified

## How to detect the version

- The `info` event is the only version carrier. `version` is `require("../package.json").version` in both trees (1.23.17/server/check-version.js:6, 2.5.11/server/check-version.js:6)
- Before login the server emits `info` with the version hidden: `sendInfo(socket, true)` on connection (1.23.17/server/server.js:279, 2.5.11/server/server.js:390). `version`, `latestVersion` and `isContainer` (and on 2.x also `dbType` and `runtime`) are absent in that payload (1.23.17/server/client.js:147-165, 2.5.11/server/client.js:145-163), so a pre-login probe cannot tell the versions apart
- After login the full `info` arrives from `afterLogin`: `sendInfo(socket)` (1.23.17/server/server.js:1718, 2.5.11/server/server.js:1839). In 1.23.17 it is emitted right after `monitorList` and before `notificationList` / `proxyList` / `dockerHostList` (1.23.17/server/server.js:1717-1722), which the CLI already waits for (the pushed-lists wait in `connect()` in src/kuma.ts), so a listener registered before login has it (measured 12/12 on 1.23.17 and 2.5.11; on 1.23 sendInfo awaits a Settings read that the pre-login sendInfo has already cached) once the list wait ends. In 2.5.11 it arrives before the login callback (2.5.11/server/server.js:474, 1833-1865)
- Rule: record the last `info` payload that has a string `version`, parse the major, treat a missing or non-semver value as 1.x (keeps 1.23 the default target). `connect()` gives a missing version a 500 ms grace after the lists and then warns on stderr. Nightly builds report 3.x, so version branches test `>= 2`
- Secondary markers that need no parsing: 2.x `info` also carries `dbType` and `runtime` (2.5.11/server/client.js:155-160); 2.x pushes `monitorTypeList` and `remoteBrowserList` (2.5.11/server/client.js:192, 214, server.js:1845-1846), 1.23.17 does not
- `primaryBaseURL` rides the same `info` payload on both versions and is not hidden pre-login (1.23.17/server/client.js:147-165, 2.5.11/server/client.js:145-163); `monitors add --type push` takes the `pushUrl` base from it instead of a `getSettings` round trip
- `isContainer` rides the same payload too; `monitors add` / `edit` refuse `tailscale-ping` when it is true — the official container image ships no tailscale binary, so the picker hides the type there on both versions
- Design consequence: several CLI checks run before connecting (field allowlists, interval bounds, timezone list, status page keys). A version-specific rule cannot run there, so each of those either moves after `connect()` or validates against the union of both versions. The union alone is not enough for fields: 1.23.17 `editMonitor` copies a fixed field list and silently drops the rest with an ok answer, so a 2.x-only field (`jsonPathOperator`) sent to 1.23 would look saved. Version-specific fields are therefore checked after `connect()` and refused with exit 2 before sending when the server does not take them

|---|---|---|---|
| Version source: `info.version` after login (read by the `info` listener in src/kuma.ts since #35; exposed as `KumaSession.serverVersion` / `majorVersion`) | emitted after `monitorList`, hidden pre-login (1.23.17/server/client.js:147-165, server/server.js:279, 1717-1718) | emitted inside `afterLogin` before the login ack, hidden pre-login (2.5.11/server/client.js:145-163, server/server.js:390, 1839, 474) | done in #35 — the listener is registered before `login`, so both orders are caught; a missing version warns and falls back to 1.x |

## Proposed work items

- Each item is independently shippable on top of item 1 unless noted; item 5 can ship first because it changes nothing on 1.23
- Order is by risk to users, not by size

1. Detect the server version after login: add an `info` listener, expose the parsed major on `KumaSession`, default to 1.x when absent or unparsable. Covers: "Version source" row. Foundation for items 3 to 9.
2. Test and CI harness for 2.x: give the fake server a 2.x profile (info with `dbType`, awaited login, `incidents`, `conditions` NOT NULL, `jsonPathOperator` rule) and add a `louislam/uptime-kuma:2.5.11` run to the integration script. Covers: every unverified row (`conditions` / `rabbitmqNodes` insert, croner 8 grammar, 2.x timezone refusals) and guards all other items.
3. 2.x monitor add / edit payload: on `add`, default `conditions` and `rabbitmqNodes` to `[]` when not given (on `edit` the fetched monitor's values go back unchanged, so existing conditions and nodes are kept), add `--json-path-operator` (default `==` on 2.x) and make the field allowlist version-aware (validation after connect, or the union). Covers: "add payload omits conditions", "json-query", "allowlist" rows.
4. 2.x monitor timing rules: interval 1..unbounded and retry interval 1 on 2.x, drop the timeout-0 refusal on 2.x, per-type timeout defaults documented. Covers: "Interval bounds", "timeout must be positive", "Default timeout" rows.
5. Redaction of 2.x secrets, unconditionally: add `bearer_token`, `gamedigToken`, `rabbitmqPassword`, `sshPassword`, `sshPrivateKey`, `sshPassphrase` to `SECRET_KEYS` and refuse them in `--set`; mask `globalpingApiToken` in `settings get` / `set`. Covers: "Secret redaction" row, "settings get redacts" row.
6. Status pages on 2.x: read `incidents` (print the array, keep `incident` as the newest pinned for compatibility), decide and implement the unpin-before-post behaviour of `status-pages incident`, drop group-monitor `url` before `saveStatusPage` unless explicitly requested, accept `analyticsId` / `analyticsScriptUrl` / `analyticsType` / `autoRefreshInterval` / `rssTitle` / `showOnlyLastHeartbeat` in save files. Covers: `get` incident row, `incident` command row, round-trip `url` row, `SAVE_FILE_KEYS` row.
7. Settings on 2.x: version-aware key list (add `domainExpiryNotifyDays`, `globalpingApiToken`; drop `dnsCache` and its default), timezone validation that does not depend on the 1.23 list. Covers: the four settings rows with impact other than none; depends on item 2 for the timezone refusal set.
